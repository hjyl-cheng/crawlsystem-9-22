# 失败任务治理与补采

本轮处理采集重试后仍无法交付的两个原因。视频详情多次请求时，解析器可能把后一次成功的 player 与前一次失败的 next 配对；现在独立回放成功请求组合，并兼容 next 先返回、旧 player 延迟返回的情况。解析器只读取保存的原始响应，采集进程的投影仅用于离线对照。

失败计划已经入库的部分视频，过去也会成为下一轮增量扫描的停止锚点，导致重新采集遗漏。现在锚点只来自 COMPLETED 来源，尚未完成的视频和缺失解析结果的原始单元会冻结成补采目标。增量与完整采集都优先执行这些目标、去重，整个清单最多 100 个视频。补采使用正常采集、原始归档、独立解析、入库回执链路；完整清单必须包含全部冻结补采目标，其余发现的视频仍受原有 scope 限制。轻量指标抽样不再重复处理补采视频。

业务交付仍要求 ABOUT / AGENT / 每个视频的来源计划已完成。旧 FAILED 计划及其证据保留，不直接重新写入过时代次，也不把历史 NOT_READY 记录改成 DELIVERED。新的恢复任务完成后产生独立交付记录，以真实业务回执确认交付。

失败记录分三类处理：已有订阅门槛拒绝结果的旧网络失败留理由关闭；后续完整任务覆盖或对应视频重新入库且已交付的历史失败留证据关闭；仍缺证据或确认不存在的来源继续保留。关闭使用 operator API 的版本检查和审计命令，状态是 IGNORED，不代表原失败执行变成成功。执行重试的 replacement 与实际补采计划单独统计。

本轮初始 OPEN 基线为 93 条。治理候选、原始样本、部署回滚镜像与每批准入命令保存在权限 0600 的 `.runtime/failure-governance/`，不进入版本库。初始关闭 27 条，涉及 11 条已由订阅门槛取消的网络失败、16 条有后来完整成功任务覆盖的历史失败。后续又以重新入库和交付回执关闭 30 条，共留理由关闭 57 条。初始 93 条中另有 17 条随重试或解析回执自动解决，19 条仍缺完整恢复证据；新增执行产生的失败单独统计。实际结果见 [验收记录](evidence.json)。

隔离验证包括 23 项采集与解析单元测试、19 项更新及失败处理数据库集成测试、18 项旧业务库交付集成测试和类型检查；数据库测试使用独立集成库。另对 25 份真实失败原件做禁止网络的内存回放，比对视频字段、指标与评论，没有向正式库、MinIO 或 Kafka 写入。

发布先导入镜像，排空两台 Worker，升级读取方后再升级 Control 和调度器，并恢复原接单状态。部署逐项检查迁移校验和、配置和无关工作负载。页面同步编译新输入契约，保留原网关和公网隧道。存在带补采字段的计划时，运行版本必须支持该字段，不能直接回退到不支持该字段的旧 Worker。

当天增量更新已经达到每日 100 次上限，因此本轮待补采频道采用现有 operator 完整 VIDEO 采集入口。仅处理审核通过且 ABOUT / AGENT 来源已完成的频道，保留原窗口及评论范围；运营脚本按当前总并发 2 准入，每频道只有一个稳定请求身份，继续使用实际请求的全局 API 配额。自动增量的每日限制继续生效。

主要运行入口均通过共享资源锁的 `npm run check:safe -- ...`：`failure-governance-inspect` 查看进度；`failure-governance-videos prepare|refresh|apply-full` 审核及提交补采；`failure-governance-retry apply` 执行已审核失败的重试；`failure-governance-close prepare|apply` 对具备新入库与交付证据的历史代次留理由关闭；`failure-governance-browser` 验证新恢复任务的本地和公网详情页。

[原始响应保留规则](../raw-retention/README.md)继续按成功完成和完整入库后的 24 小时执行。失败任务及其专用证据不会因为本轮留理由关闭而直接删除。

12 个审核通过的完整 VIDEO 补采计划全部 COMPLETED / DELIVERED，共完成 477 个视频目标，其中冻结补采清单共 264 个目标。16 个原失败频道各执行一次受控重试，14 个采集完成、2 个失败；部分采集完成的增量仍因旧视频来源不完整而 NOT_READY，后来由上述独立补采完成业务交付。旧的 14 条 NOT_READY 交付记录仍保留，新交付失败与待交付数量均为零。

剩余异常集中在三个频道：UCQm0f2MItHBDSLJ0GL4OaqA 的音乐人上传播放列表包含另一音乐频道持有的视频；UCzoP7l5bzSzi2gUUNn0I79w 的网页报告不可用，但官方频道 API 仍返回一条记录；UCUp6wodtd6vPPj1ZmFfVoIQ 的两条旧 NOT_FOUND 缺原始证据。保留失败状态和来源保护，不以播放列表关联替代实际视频归属，也不把网页与 API 的不一致判为确认删除。

音乐人播放列表原件声明 211 个视频，首屏 100 个 LockupView 都携带该上传播放列表的 watchEndpoint；已审核的 10 个目标里有 3 个由另一音乐频道持有。禁止网络的离线回放重建原 30 个目标，确认这一情况不是推荐区混入。上传列表过滤策略未作改变。发现的程序缺陷是 API 回退遇到归属冲突时没有保存已抓取的原件，现在在抛出失败前归档网页请求与 API 回应，并在归属不一致时停止抓取该视频的评论。采集器、网页字段映射与独立解析器均保留归属校验。

诊断入口包括 `failure-governance-diagnose PLAN_ID`（校验和验证后只读提取失败原件）、`failure-governance-owners PLAN_ID`（首次最多 10 个视频的一次官方 API 查询，后续复用诊断结果）、`failure-governance-upload-replay`（下载已归档 TARGETS 后禁用网络回放）。诊断不改正式视频数据，原件与密钥不提交。准入脚本可追加 `once` 单次执行，避免为排队长时间持有共享检查锁。
