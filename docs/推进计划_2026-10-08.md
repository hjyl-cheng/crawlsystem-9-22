# 推进计划：让整套系统完整跑起来

制定：2026-10-08。目标：业务链路**找频道 → 审核候选 → 全量采集 → Agent 画像 → 纳管定时更新 → 发布给下游**全部自动运行，采集系统控制台每个页面都显示真实数据、能完成对应操作；之后补齐长期稳定运行所需的底座。

最新状态（2026-10-10）：R1～R6 已完成部署与验收，现况以 [R6](r6/README.md) 的记录为准。自动搜索、准入、定时更新和 Query Runner 已恢复，强制 BR 出口仍关闭。本轮完成 4 个自动首次采集及 1 个故障恢复采集、98 个定时 ABOUT 更新、3 次新政策自动搜索；原有 9,692 个视频身份全部保留。用户确认以短期真实运行验收替代三天 / 一周观察。后续先按老服务器业务库结构对接下游，自动收集搜索词、配置中心及其他页面增强继续按计划推进。

做法：各环节的业务逻辑沿用旧系统（crawlSystem `e92d9227`）已经稳定运行的做法，用新架构重写，不接旧服务；每完成一项就部署并在真实频道上验证。对应[开发计划](业务平台开发计划_讨论稿_2026-09-23.md)第 6 章：阶段 A、B、D 属于 M3，阶段 C 属于 M4，阶段 E 属于 M5。

## 0. 目标架构（2026-10-09 版，与用户讨论确定；R1～R6 改造已验收）

起因：与外部专家讨论后，调整采集数据的存储与流转。新系统此前的三个偏差：采集把 Data API 当主力（设计 24.8 与老系统都只拿它兜底）；原始响应不保存、抓取和解析在同一步完成；评论正文存进 PG（占视频数据 76%，老系统 PG 因此类大 JSON 涨到 459 GB）。

**命名（10-09 更正）**：控制台所在的整个系统叫**采集系统**（控制台 = 采集系统控制台）；下游叫**业务系统 / 业务库**。采集系统自己保留一份频道数据（采集 PG 的"采集数据"块）；交付给业务库走 **采集 PG 待发布表 → Debezium → Kafka 交付主题 → 业务库入库程序**（24.8 原方案）：定稿与写待发布表在同一事务，Debezium 读 PG 变更推送，不丢不多；两个系统只通过交付主题联系，互不读对方数据库。交付内容为定稿频道（频道资料、视频资料、Agent 画像，不含评论正文），候选本身不交付。

### 0.3 采集数据去向

| 数据 | MinIO | PG（长期） | 用途 |
| --- | --- | --- | --- |
| 原始响应（所有请求） | 14 天 | — | 重新解析、排查证据 |
| 频道资料 | 解析结果 90 天 | 当前一份 | 系统与下游 |
| 视频资料 | 解析结果 90 天 | 当前一份，只含评论数与状态 | 系统与下游 |
| 评论正文 | 解析结果 90 天 | 不进 | Agent 输入；以后可能辅助训练（要用须在删除前另行导出） |

体量（按每天新采 2,000 个频道，定时更新另计）：原始约 3.4 GB/天（14 天约 48 GB）；解析结果约 120 MB/天（90 天约 11 GB）；PG 去掉评论后约 60 MB/天。各节点剩余磁盘（10-09）：a1 126 GB，a2/a3/s1/s2/s3 各 53～58 GB。

### 0.3b 采集任务的数据怎么落地（全量 / 更新）

全量和更新都由 Temporal 工作流分步完成（现有步骤：频道基础信息 → 列出目标视频 → 视频分批采集，每批 10 个 → 更新时近期视频复采 → Agent 画像）。改造后：

1. **每抓到一个响应就立刻存 MinIO**，不在执行器内存或本地盘暂存（执行器内存上限 512 MB、临时盘 64 MB，重启即丢）。文件按"计划 / 步骤 / 视频 / 类型"固定命名，重试时文件已存在就跳过，作用等同现在的回执。
2. **执行器只从原始响应里读"下一步抓什么"**（订阅数是否够、视频 ID、翻页令牌），采集一路往下走，不等数据库。
3. 每一步结束时发一条"清单"消息到 Kafka（这一步存了哪些文件）；解析、入库在后台进行，PG 写完记入入库账本。
4. **只有两处等数据库**：Agent 画像要等视频数据全部入库（读 PG 资料 + MinIO 评论）；"计划完成、结算时钟"要等所有步骤入库。
5. Temporal 工作流只记进度和文件地址，不放大块数据（24.8 要求）。

### 0.3c Kafka 里发什么、按什么粒度

不按"一个频道采完"发（中途失败时已采部分发不出去、要等几分钟才开始解析、频道大小不一）。粒度：**采集 → 解析按"每个原始文件"发，解析 → 入库按"每个频道 / 视频 / 画像"发；"批量"在入库端做**（攒约 500 条或 1～2 秒批量写 PG）。

| 主题 | 谁发 | 一条消息 = | 内容 | 谁收 |
| --- | --- | --- | --- | --- |
| `crawl.raw` | 采集 | MinIO 里存好的一个原始响应 | 文件地址、类型、频道 / 视频 / 计划 ID、抓取时间、校验值（约 0.5 KB，不含原始内容） | 解析程序 |
| `crawl.step` | 采集 | 一个步骤结束 | 计划 ID、步骤、本步骤文件清单 | PG 入库程序（判断这一步是否齐全） |
| `facts.channel` | 解析 | 一个频道的一份资料 | 频道字段（约 2～10 KB） | PG 入库程序 |
| `facts.video` | 解析 | 一个视频的一份资料 | 视频字段、评论数与状态，不含评论正文（约 2～5 KB） | PG 入库程序 |
| `facts.observation` | 解析 | 一次指标观测 | 某时刻的播放 / 点赞 / 订阅数 | PG（更新时钟）、ClickHouse（曲线） |
| `facts.agent` | Agent | 一次画像结果 | 画像字段 | PG 入库程序 |
| `ops.events` | 各环节 | 一条运行事件 | 请求成败、耗时、原因等 | ClickHouse 入库程序 |

**10-09 细化（顺序与粒度）**：① 先存 MinIO，确认存好后才发 `crawl.raw` 消息；存好但消息没发出（如进程重启）时，靠每步结束发的 `crawl.step` 清单和入库账本对账补解析，重试时也会给已存在的文件补发消息；消息重复时解析程序按文件地址去重；没存好就失败则不发消息、该项重抓。② 一个文件 = 一个采集单元（频道首页 + About、一次上传列表的全部分页、一个视频的详情 + 评论含 WEB / IOS 各次尝试），文件里原样保留每个响应；全量一个频道约 32 条消息（原按每个响应约 62 条）。

评论正文不进 Kafka，由解析程序直接写入 MinIO 解析结果。按频道 ID 分区，保证同频道顺序；同一文件 / 同一实体重复送到时按地址或 ID 覆盖，不产生重复数据。量（按每天新采 2,000 个频道）：`crawl.raw` 约 12 万条 / 天，`facts.*` 约 6 万条 / 天；保留 3 天，每台 Kafka 约占 1 GB（现有 12 GB）。更早的数据需要重放时从 MinIO 重新解析。

### 0.3d 状态、失败、日志放哪（10-09）

10-09 改造前：状态都在 PG（每个对象一行覆盖更新）；失败分散——计划失败只是 `events` 里的一条事件（控制台"错误"页即由此查询），搜索失败在 `query_runs.last_error`，导入失败是导入队列的一个状态，Data API 失败在 `data_api_permits.failure`；程序日志由 Alloy 收进 Loki，只保留 3 天；指标在 Prometheus，告警发钉钉。R5 已实现下述失败聚合、证据、ClickHouse 统计与清理，Loki 保留已改为 7 天。

方案：六类记录各有一处，用计划 ID、频道 ID、文件地址、链路 ID 串起来。

| 类型 | 例子 | 存哪 | 保留 | 界面 |
| --- | --- | --- | --- | --- |
| 当前状态 | 计划步骤、频道 / 搜索词 / 候选 / 导入状态、代理健康、节点在线 | PG，每对象一行覆盖（不变） | 随对象 | 各页状态、筛选、操作 |
| 待处理的失败 | 采集 / 解析 / 入库 / 画像失败、搜索放弃、导入失败 | PG 新增"失败清单"：每个失败对象一行（原因代码、次数、首次 / 最近时间、下次重试、等待重试 / 需人工 / 已解决） | 已解决的 30 天后删 | 新"失败处理"页（替代"错误"页）：按原因分组、重试、忽略 |
| 过程事件 | 计划时间线、每次请求成败与耗时 | PG `events` 只留进行中与近 30 天；全量进 ClickHouse | PG 30 天；CH 明细 180 天，汇总长期 | 计划详情时间线（PG）；失败趋势与原因分布（CH） |
| 失败证据 | 导致失败的原始响应 | MinIO：出错的那份复制到 `evidence/` | 90 天 | 失败详情"查看原始响应" |
| 程序日志 | 运行日志、堆栈、请求链路 | Loki（已部署），不进 PG / CH | 由 3 天调到 7～14 天（Loki 卷 5 GB，需评估） | 失败记录带链路 ID，跳 Grafana |
| 指标告警 | 吞吐、积压、错误率、磁盘 | Prometheus + 钉钉（已有） | 不变 | 控制台关键数字，详细看 Grafana |

新流程：解析或入库重试仍失败的消息转入 Kafka 死信主题（`dlq.parse`、`dlq.sink`）并记入失败清单，不阻塞后续消息，修复后可一键重新解析或入库；每个计划步骤在入库账本里计数（已存 MinIO / 已解析 / 已入库 / 失败），计划详情直接显示，不为每个文件永久留一行。

### 0.3e PG 的两大块（10-09 核对现有 37 张表）

| 块 | 表（现在都在 `m1` 里） | 谁写 |
| --- | --- | --- |
| 采集控制 | 账号登录：`console.accounts`、`console.sessions`、`console_sessions`、`console_login_limits`；计划执行：`plans`、`domains`、`commands`、`intents`、`obligations`、`plan_video_targets`、`plan_items`、`receipts`、`events`、`plan_api_reservations`；更新时钟：`channel_clocks`、`channel_feature_state`、`feature_reference_distributions`、`update_scheduler_state`；找频道：`query_*`、`channel_candidates`、`channel_imports`；代理与节点：`proxies`、`proxy_sources`、`proxy_observations`、`proxy_daily`、`workers`；Data API 额度：`data_api_budget`、`data_api_permits`；新增记账：采集清单、入库账本、失败清单 | 控制 API、调度程序 |
| 采集数据 | 频道资料（基础信息、Agent 画像，当前一份）、`videos`（当前一份，不含评论正文）、指标观测（现 `plan_video_samples`） | **只由 Kafka 入库程序写**，其他程序只读 |

要点：

1. `channels` 现在两块混在一起（`about`、`agent` 是采集数据；`management_state`、`management_version`、`latest_plan_id` 是控制数据），拆成"频道资料"（采集数据）和"频道纳管"（控制）两张，避免入库程序和运营操作同时改同一行。
2. 同一个 PG 里分两个 schema（如 `control`、`crawl_data`），数据库账号按块分权：入库程序只能写 `crawl_data`，控制 API 只能写 `control`，执行器仍然没有数据库账号；以后数据量大可把 `crawl_data` 整块搬到单独的库。
3. 两块的连接点是入库账本：数据入库后通知控制块"这一步齐了"，再结算更新时钟、触发 Agent（时钟读采集数据、写控制表）。
4. 体量：采集数据只存当前资料，约每频道 30 KB，纳管 10 万个频道约 3 GB；控制块的流水账按 30 天清理。近期一个 PG 足够。

### 0.3f 更新采集与下游一致性（10-09）

- 更新采集与全量走同一条路：每个响应先存 MinIO，再解析、经 Kafka 写采集 PG。区别只在抓什么：基础信息到期刷新、视频列表扫到上次已知最新视频为止、近期视频数值复采、Agent 到期重新画像。
- 采集 PG 每个频道 / 视频只留最新一份，按观测时间新的覆盖旧的（迟到的旧消息不会覆盖）；历史数值进 ClickHouse。
- 业务库与采集 PG 的定稿版本**最终一致**：每次采集（全量或更新）定稿后交付，正常延迟几秒到几分钟；更新进行中采集 PG 可能暂时领先，但业务库不会收到半截数据。交付带版本号，业务库只接受更新的版本；频道移出纳管或在 YouTube 上删除时交付"下线"消息；内容与上次交付相同时不发。采集 PG 的内部字段（纳管状态、时钟、变化概率、观测时间、评论抓取状态等）不交付。
- **交付是增量的**：只有本次定稿的频道发消息；Debezium 读 PG 变更日志（WAL），不扫表。消息只放这次变了的部分（变了的频道字段、新视频、数值有变化的视频、重新画像的结果，约几 KB～二十 KB），新频道第一次交付时为全量；每行带版本号。量：现在规模约 2 万次 / 天（平均每秒 0.2 次），纳管 100 万频道时约 10 万次 / 天（每秒 1～2 次，每次十几行），业务库入库程序批量写、按频道分区并行即可。
- **首次导入**：采集 PG 里已有的频道一次性批量导入业务库，之后再走增量。
- **复制槽风险**：Debezium 长时间停机时，PG 会保留未读的变更日志，可能撑满磁盘（PG 卷 30 GB）；要给保留量设上限（`max_slot_wal_keep_size`）并对积压告警；待发布表写入后及时清理。

### 0.4 对照现有系统：哪些不动、哪些要改（10-09 核对代码与部署）

本节保留 10-09 的改造基线；下列 1～12 项已按 R1～R5 实施，当前运行状态与边界见各阶段验收记录及 R6。

### 0.6 业务系统界面数据：PG + ClickHouse（10-09）

分工原则：

- **PG：现在是什么样、要能操作的**——列表、详情、状态、待办、人工操作，以及控制决策要用的实时计数（Data API 当日额度、每日计划数、同时运行数）。这些必须准确、立即可见。
- **ClickHouse：发生过什么、趋势怎样**——按小时 / 天的数量、成功率、耗时分布、失败原因、增长曲线、历史指标。只追加、按时间查、压缩率高；比 PG 晚几秒，但不参与控制决策。
- **不需要 ES**：频道名、搜索词的关键字查找用 PG 自带的模糊索引即可。
- **MinIO 不直接给页面用**：排查时由控制 API 按需读取原始响应或评论（保留期内）。
- **系统运行指标**（CPU、内存、Kafka 积压、MinIO 容量）继续放 Prometheus / Grafana，控制台只显示关键数字。

进 ClickHouse 的方式：各环节把"事件"（采集请求、任务开始 / 完成 / 失败、解析、入库、Agent、Data API 调用、代理使用、搜索、候选准入）发到 Kafka 的事件主题，由 ClickHouse 入库程序批量写入，用物化视图预先算好小时 / 天汇总；频道 / 视频指标观测也进 ClickHouse，用来画增长曲线。控制台的统计接口读 ClickHouse，结果缓存 30～60 秒。

PG 里只增不删的表见 0.4 第 11 条。现在都不大（最大约 8 MB），按停前的速度每天约新增十万行。改为：明细写入 ClickHouse 做统计；PG 只保留任务恢复和当前页面需要的近期部分（如 30 天），定期清理。

| 页面 | PG（当前状态、列表、操作） | ClickHouse（统计、趋势） |
| --- | --- | --- |
| 总览 | 正在运行的任务、纳管频道数、各状态数量、待处理告警 | 今日 / 7 天吞吐、成功率、各环节耗时、频道增长曲线 |
| Query 发现 | 搜索词列表、状态、时钟、来源、添加 / 停用 | 每天搜索次数、新频道与合格数趋势、按分类 / 国家的效果排行 |
| 候选频道 | 候选列表、状态、准入 / 拒绝 | 每天发现 / 准入 / 拒绝数量、合格率 |
| 全量采集 | 计划列表与详情、步骤状态、取消 | 每天完成 / 失败数、耗时分布、失败原因分布 |
| 频道管理 / 频道详情 | 频道当前资料、纳管状态、更新时钟、视频列表 | 订阅 / 播放增长曲线、视频指标历史 |
| 定时更新 | 到期队列、各频道时钟、限额 | 每天更新量、发现新视频数、空跑率 |
| Agent | 待画像队列、当前画像 | 每天画像数、耗时、失败率、画像变化 |
| Data API | 当日额度（实时计数，发放许可要用） | 按小时 / 接口 / 失败原因的调用统计 |
| 发布交付（阶段 C） | 待发布 / 已发布状态 | 每天交付量、延迟 |
| 代理 / 执行节点 | 代理库存、分配、当前健康、心跳 | 代理成功率、封禁率、延迟、流量趋势 |
| 配置 / 账号 | 全部在 PG | — |
| 新增：存储与管道 | — | 解析失败、重新解析（ClickHouse）；MinIO 容量、Kafka 积压（Prometheus） |

ClickHouse 体量：按每天新采 2,000 个频道，约 12 万条采集请求事件 / 天，压缩后约每天十几 MB，现有单节点（s3，20 GB 卷）够用。

**补充发现（10-09，继续读老系统代码）**：

1. **浏览器指纹传输**：老系统线上采集节点强制走"指纹网关"（`FINGERPRINT_TRANSPORT_REQUIRED=true`）——每个节点旁一个 Python 小服务（`scripts/fingerprint_gateway.py`，curl-cffi 0.15.0），模仿 Chrome 136 的 TLS / HTTP2 指纹并按身份保存 cookie；YouTube.js 的请求都经它转发。新系统现在由 Node 直接发请求，特征不像浏览器，可能是实测"被当成机器人"多的原因之一。**R2 纳入：执行器旁加同样的指纹网关。**
2. **客户端身份**：老系统采集身份 `qy-br-channel-anonymous-v1`：内容语言 pt-BR、地区 BR、时区 America/Sao_Paulo；每个身份一套浏览器档案（Chrome UA、生成的 visitor_data、持久 cookie）。**R2 纳入。**
