# 推进计划：让整套系统完整跑起来

制定：2026-10-08。目标：业务链路**找频道 → 审核候选 → 全量采集 → Agent 画像 → 纳管定时更新 → 发布给下游**全部自动运行，业务控制台每个页面都显示真实数据、能完成对应操作；之后补齐长期稳定运行所需的底座。

做法：各环节的业务逻辑沿用旧系统（crawlSystem `e92d9227`）已经稳定运行的做法，用新架构重写，不接旧服务；每完成一项就部署并在真实频道上验证。对应[开发计划](业务平台开发计划_讨论稿_2026-09-23.md)第 6 章：阶段 A、B、D 属于 M3，阶段 C 属于 M4，阶段 E 属于 M5。

## 0. 目标架构（2026-10-09 版，与用户讨论确定；新功能开发暂停，先按此改造）

起因：与外部专家讨论后，调整采集数据的存储与流转。新系统此前的三个偏差：采集把 Data API 当主力（设计 24.8 与老系统都只拿它兜底）；原始响应不保存、抓取和解析在同一步完成；评论正文存进 PG（占视频数据 76%，老系统 PG 因此类大 JSON 涨到 459 GB）。

              ▼                                      │
代理层 ──► ② 采集层：按老系统流程（YouTube.js / 网页接口走代理，Data API 按老系统规则兜底）
              │ ③ 原始响应                                │
              ▼                                      │
        MinIO raw/（14 天自动删）                         │
              │ ④ 消息只带存储地址等（Kafka crawl.raw）        │
              ▼                                      │
        ⑤ 解析层 ──► MinIO parsed/（解析结果含评论正文，90 天自动删）
              │ ⑥ 结构化数据，不含评论正文（Kafka facts.*）    │

### 0.2 各层职责与边界

| 层 | 做什么 | 用什么 | 不做什么 |
| --- | --- | --- | --- |
| 业务控制系统 | 运营操作、配置、查看；保存控制状态 | 控制台 + 控制 API + PG 控制表（已有） | 不碰原始数据 |
| 调度与编排 | 到期建任务；任务的重试、超时、并发上限 | 调度程序（已有）+ Temporal（已有，是否改队列待定） | 不抓取、不解析 |
| 代理层 | 代理库存与分配；每台机器本地租用、健康、冷却 | 中心代理库 + 各机器代理管理器（已有） | — |
| 采集层 | 按老系统步骤抓取：搜索、频道页、视频列表、视频页、评论、近期视频复采；只解析"下一步抓什么"（视频 ID、翻页令牌） | YouTube.js / 网页接口 + 代理；Data API 仅按老系统规则兜底 | 不解析字段、没有数据库账号 |
| 存储层 MinIO | 周转区：原始响应 14 天、解析结果（含评论）90 天，到期由生命周期规则自动删除 | MinIO（新部署） | 不是长期存储 |
| 消息层 Kafka | 传"已抓取"引用和解析后的结构化数据；按频道 ID 分区，保证同频道顺序；保留几天 | Kafka（已部署 3 节点） | 不放原始响应、不放评论正文 |
| 解析层 | 读原始响应 → 频道 / 视频 / 评论 / 指标；评论写 MinIO，其余发 Kafka；解析器带版本号，修 bug 后对 14 天内原始数据重新解析，不必重抓 | 现有解析代码迁过来 | 不抓取 |
| 入库层 | 批量写 PG，按频道 / 视频 ID 去重覆盖（重复消息不产生重复数据）；记录入库账本，对照采集清单判断"这一步齐了" | 每个数据库一个入库程序 | 不改控制决策 |
| Agent 层 | 读 PG 资料 + MinIO 评论 → 本地模型 → 画像 | profile-agent（已有） | 评论目前不参与训练，以后可能辅助 |
| 数据库 | PG：控制表 + 频道 / 视频 / 画像当前资料（不含评论正文，长期保存）。ClickHouse：指标历史与分析（可选）。ES：用途待定 | | |
| 交付层 | 定稿数据发给下游 | PG 待发布表 → Debezium → Kafka → 业务库（设计 24.8 原方案） | 格式在阶段 C 定 |

### 0.3 采集数据去向

| 数据 | MinIO | PG（长期） | 用途 |
| --- | --- | --- | --- |
| 原始响应（所有请求） | 14 天 | — | 重新解析、排查证据 |
| 频道资料 | 解析结果 90 天 | 当前一份 | 系统与下游 |
| 视频资料 | 解析结果 90 天 | 当前一份，只含评论数与状态 | 系统与下游 |
| 评论正文 | 解析结果 90 天 | 不进 | Agent 输入；以后可能辅助训练（要用须在删除前另行导出） |
| Agent 画像 | 原始输出 + 解析结果 90 天 | 当前画像 | 系统与下游 |
| 搜索结果 | 原始 14 天 | 候选频道、搜索统计 | 找频道 |

体量（按每天新采 2,000 个频道，定时更新另计）：原始约 3.4 GB/天（14 天约 48 GB）；解析结果约 120 MB/天（90 天约 11 GB）；PG 去掉评论后约 60 MB/天。各节点剩余磁盘（10-09）：a1 126 GB，a2/a3/s1/s2/s3 各 53～58 GB。

### 0.4 和现在相比的变化

1. 采集按老系统流程重写（YouTube.js / 网页接口为主，Data API 只兜底）；搜索不再用 Data API 查订阅数，改在采集频道页时判断。
2. 执行器拆成采集和解析两部分；现在"抓取后直接解析写库"改为"原始存 MinIO → 解析 → Kafka → 入库"。
3. 现在的写库逻辑（回执、完成判断）改成 PG 入库程序 + 入库账本。
4. PG 视频表去掉评论正文，已有数据清理；Agent 改从 MinIO 读评论。
5. 新部署 MinIO（含生命周期规则）；建 Kafka 主题与保留策略；已部署但闲置的 Kafka、Debezium 用起来。
6. 设计 24.8 中"Kafka 只用于对外发布"的约定改为本节流程。

## 2. 阶段计划

### 阶段 A：持续更新闭环（M3 第 3～5 步）

| 步骤 | 内容 | 完成标准 |
| --- | --- | --- |
| A1 视频增量 | 更新计划冻结"锚点"（最近 20 个已知视频）和待复查的近期视频（旧系统打分，最多 20 个）；Worker 从最新上传往下翻到锚点为止，追赶超过 100 个则只留最新 30 个；新视频按原方式采详情与评论；近期视频只用 Data API 复查计数（不走代理、不重采评论）；入库时与旧值比较得出变化，交给时钟算法；打开视频自动更新 | 真实频道新发布视频被发现；复查计数正确；视频时钟的"近期复查"不再跳过 |

| A4 验收 | 接入约 20 个真实频道（高频、低频、长期不更新各有）连续自动更新 3 天 | 失败只按规则重试；实体数不随更新次数增长 |

B2 注（2026-10-09 确认）：
- **搜索时钟**（策略 `query-clock-1`，24.8 §5.2）：新词先搜一次"今年"；一次运行找到 ≥3 个新的合格频道（订阅 ≥1000）→ 每周搜"本周"，1～2 个 → 每月搜"本月"，0 个 → 仍每月并记一次空跑；连续 3 次空跑 → 冷却（3 个月后再试），冷却后仍空 → 休眠（不再自动搜，待新来源唤醒）。人工可停用，或指定每周/每月（需原因）。失败只安排重试（1 小时起翻倍，最长 1 天），不改周期。月按 UTC 日历月计。
- **准入**：订阅 ≥1000 的候选自动进入频道导入队列，候选页可人工拒绝或通过（"自动准入 + 可人工干预"）。
- **首日实测（2026-10-09）**：上线后 4 分钟内完成 49 次搜索，每次 2～5 秒，发现 2,803 个新频道，其中 2,056 个合格；Data API 只用 81 单位。合格候选超过 2,000 后搜索按积压规则自动暂停，准入后再恢复。候选准入后 25 分钟完成 87 个全量采集（含视频评论与 Agent 画像），每个 7～25 秒；纳管频道从 2 个到 110 个。**真正的上限是 Data API 配额**：全量采集平均 5 单位/频道，搜索 1.7 单位/次，每天 1 万单位约够新采 1,800～2,000 个频道（按现在速度约 5 小时用完），纳管越多、定时更新占用越多。（"每天 100 个计划"只限定时更新，导入只受同时 2 个与配额限制。）
- **搜索窗口实测（Q-27，2026-10-09）**：youtubei.js 18.1.0 的 `upload_date: week` 返回的视频都在 6 天内发布，`month` 都在约 1 个月内；业务上仍存 THIS_WEEK / THIS_MONTH / THIS_YEAR，换适配器不改历史。
- **搜索词来源**：人工添加 + 从已采集频道自动收集（关键词、标签、视频标题等，限制增长）。
- **老系统搜索词迁移**：老系统 271 万个词中只有约 4 万个真正搜过（2026-09-24～10-08），其余为未经筛选的视频关键词回填，不迁。搜过的词按其搜到的已画像频道定业务分类（某分类占 ≥40% 且 ≥2 个频道，最多两类；否则取第一类且需 ≥2 个），国家 BR、语言 pt；得到 2.08 万个词、2.18 万条绑定，按"新词"首次搜"今年"，按老系统搜到的新频道数排先后。约 1.89 万个搜过但定不出分类的词暂不迁。

## 3. 业务控制系统前后端开发计划

业务控制系统 = 控制台前端（`apps/console`）+ 控制 API 后端（`apps/control-api`，契约在 `packages/contracts`，数据在 `packages/store`）。现有接口 36 个，覆盖计划、频道、纳管与更新、代理、Worker、账号、错误与回执。每个页面随对应的业务能力一起完成，不单独先做界面。

### 3.1 逐页计划

| 页面 | 前端要做 | 后端要新增的接口 | 依赖 | 阶段 |
| --- | --- | --- | --- | --- |

### 3.2 共同要求

- **契约先行**：每个新接口先在 `packages/contracts` 定义请求与响应，前后端共用；读接口区分只读与操作员权限，写接口带版本号或请求编号防重复。
- **示例数据退场**：页面接上真实数据时，删除对应的 `*-sample.ts` 和"预览示例数据"开关；全部完成后控制台不再有示例数据。
- **测试**：后端每个接口有集成测试；前端每个页面有浏览器测试（含手机宽度、无横向滚动）。
- **名称统一**：频道资料 / 视频与评论 / Agent 画像等叫法全站一致。
