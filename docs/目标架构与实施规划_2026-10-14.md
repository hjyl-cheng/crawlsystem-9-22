# crawlSystem 采集系统目标架构与实施规划

**2026-10-14** · 在线版 <https://claude.ai/code/artifact/7b2e6659-e040-4791-a9fa-1e7014c6133d> 是早期版本，以本文件为准

## 1. 目标、范围与边界

采集系统的目标是覆盖上亿个频道（靠时间逐步积累）、其中至少一千万个持续更新，支持多平台；现有 6 台机器只用于验证设计，正式规模靠加机器扩展。

**分层（10-14 调整为两层）**

每个纳管频道首次全量采集时都生成 Agent 画像，Agent 时钟到期再重新画像，所以原来的"L2 深度层"并入 L1。

| 层 | 规模 | 采什么 | 更新方式 |
| --- | --- | --- | --- |
| L0 索引层 | 约 1 亿个频道（随时间积累） | ID、名称、订阅数、国家 | 每月轻量探测一次 |
| L1 纳管层 | 约 1,000 万个频道 | 频道资料；视频（首次采 90 天内最近的最多 30 个，之后每次视频更新把新视频加进来，只增不减，只存当前一份）；首屏评论；Agent 画像 | 三个时钟到期更新：资料、视频、Agent（首次全量时生成画像，之后每 60～365 天重新画像）；休眠频道低频探测 |

**图 1 两层频道：L0 先记下来，达到规则后纳管**

```

│ 只记 ID、名称、订阅数、国家                                      │
│ 每月轻量探测 1 次（约 1 个请求）                                 │
│         │ 达到纳管规则（门槛待定）                               │

│ ┌─ L1 纳管层：约 1,000 万个 ─────────────────────────────────┐   │
│ │ 频道资料、视频（首次 90 天内最多 30 个，之后持续加入新视频） │ │

│ │ 三个时钟到期更新：资料、视频、Agent（60～365 天）          │   │

│ └────────────────────────────────────────────────────────────┘   │

**八项质量目标**：高性能、高并发、高可伸缩、高可靠、高安全、高可观测、易用、可维护（第 9 节逐项对应）。另加一条：存储只随实体（频道、视频）数量和业务要求保留的指标历史增长，运行过程数据都有期限，不无限堆积。

**系统边界**

- 采集系统负责：发现频道、采集、解析、入库、画像、生成交付数据。
- 采集系统的终点是交付区：把变更日志和快照放到对象存储，业务方自行拉取。
- 业务系统负责：业务库的部署、表结构、旧结构映射、入库。业务库以后单独部署，与采集系统只通过交付区联系，互不读对方数据库。
- 命名：控制台所在的整个系统叫采集系统；下游叫业务系统 / 业务库。

**设计原则**：设计按亿级做，部署按阶段做。现在只把以后改不动的东西定好（身份、分区键、分区数、存储边界），组件集群化随规模推进。

## 3. 组件职责：每个技术只干一件事

不引入新技术；每个组件定死一个职责、一类数据、一个保留期。判断一份数据放哪里只问三句：原样的大块数据放 MinIO；"现在是什么样、要能操作"放 PG；"发生过什么、趋势怎样"放 ClickHouse。Kafka 只是串联它们的管道。

**图 3 一份数据该放哪里**

```
一份数据该放哪里？按顺序问：

  原样的大块数据？（原件、评论正文、交付文件）
     ├─ 是 ──► MinIO：短期周转，到期自动删除
     └─ 否
        "现在是什么样"、要能操作？（状态、当前资料）
           ├─ 是 ──► PG：每个对象只留当前一份
           └─ 否
              "发生过什么"、要看趋势？（事件、指标历史）
                 ├─ 是 ──► ClickHouse：只追加；指标历史长期保留，运行事件 180 天
                 └─ 否
                    只是在环节之间传递？
                       ├─ 是 ──► Kafka：3 天
                       └─ 否 ──► 程序日志 / 运维指标：Loki / Prometheus，7 天
```

| 组件 | 唯一职责 | 存什么 | 保留 | 明确不干 |
| --- | --- | --- | --- | --- |
| K3s | 调度与隔离：哪台机器跑什么、故障重启 | 不存业务数据 | — | 不兼做开发机 |
| Temporal | 编排：一批频道的采集步骤、重试、超时、取消、并发上限 | 进度和 MinIO 文件地址 | 关闭执行保留若干天 | 不放大块数据，不做定时调度 |
| MinIO（固定版本 RELEASE.2025-07-23） | 大块、原样的字节：原始响应、解析结果、评论正文、失败证据、交付文件 | 文件 | 见第 4 节（成功的 2 天自动过期） | 不做长期库，不直接给页面查 |
| Kafka | 流水线各段之间的消息，外加交付主题 | 引用消息（约 0.5 KB）、结构化事实（几 KB） | 3 天 | 不放原始响应和评论正文，不当数据库 |
| PG（采集） | "现在是什么样"：控制状态 + 每个频道 / 视频 / 画像的当前一份 | 当前资料 + 近 30 天运行流水 | 当前资料长期，流水 30 天 | 不存历史、评论、报表；不放业务库、Temporal、测试库 |
| ClickHouse | "发生过什么"：频道指标历史（播放量、粉丝量、视频总数）、运行事件、小时 / 天汇总 | 只追加 | 指标历史长期；运行事件 180 天；汇总长期 | 不参与控制决策 |
| JDBC Source 连接器（Aiven 开源版，跑在 Kafka Connect 里） | 每 5 秒查一次采集 PG 的 outbox 表，把 30 秒前写入的新行发到 Kafka 交付主题 | 读取位置存在 Kafka Connect 里 | — | 不读 WAL、不占复制槽，用只读 outbox 的专用数据库账号 |
| S3 Sink 连接器 | 把 Kafka 交付主题按批写成 MinIO 文件 | — | — | 不做业务映射 |
| Prometheus / Loki / Grafana / Alertmanager | 运维指标、程序日志、告警 | 指标、日志 | 7 天 | 不存业务数据 |

**什么是"流水"**：运行过程记录，例如计划和步骤、计划事件时间线、入库回执、Data API 调用明细、每次搜索找到的频道、导入队列。它们只用于任务恢复和页面查看，不是业务数据，PG 只留近 30 天；需要统计的部分同时写进 ClickHouse 运行事件（180 天）。频道的三项指标历史（播放量、粉丝量、视频总数）是业务数据，不属于流水，长期保留（第 4 节）。

### 3.1 中间件评估（10-14）

每个组件问两个问题：在新架构里有没有别人替代不了的职责；选的这个产品合不合适。结论：PG、Kafka、Temporal、ClickHouse、K3s 几大件都合适；要动的是去掉 Debezium、Citus 路线改为多集群分库、MinIO 继续用但守三条约定，并补齐镜像仓库、控制台入口和异地备份接口。

| 组件 | 要不要用 | 选型合适吗 | 说明 |
| --- | --- | --- | --- |
| K3s | 保留 | 合适 | 标准 K8s，能撑几百个节点；规模大了以后 etcd 不放在采集节点（现在 s1、s2 各有一个） |
| cert-manager | 保留 | 合适 | 内部 TLS 证书 |
| CNPG + PostgreSQL 18 | 保留 | 合适 | 控制状态和当前资料；横向扩展用"按频道分到多个 CNPG 集群"，不上 Citus（CNPG 只支持标准 PG） |
| barman 插件 | 保留，要配上 | 合适 | PITR 的备份目标做成可配置：先指向集群内 MinIO 的 `crawl-pg-backup`，以后买云备份时只改地址和密钥 |
| PgBouncer | 保留 | 合适 | 连接上限只有 100，规模上去后必需 |
| Kafka（Strimzi，KRaft） | 保留 | 合适 | 流水线骨干；Redpanda 是 BSL 许可，NATS 没有 Kafka Connect 生态 |

| Debezium | 去掉 | 不合适 | 批量交付用不上实时 CDC，且复制槽是反复出事的地方；改用 JDBC Source 连接器 |
| JDBC Source 连接器（Aiven 开源版） | 新增插件 | 合适 | Apache-2.0、活跃维护（`Aiven-Open/jdbc-connector-for-apache-kafka`，v6.13.0 于 2026-10-02 发布）；按间隔查表，不占复制槽；和 S3 Sink 跑在同一个 Kafka Connect 里，不增加新服务、不写代码 |
| Temporal | 保留 | 合适，有前提 | 前提是一个工作流处理一批频道；一个频道一个工作流到千万级不合适。它有 7 个服务，是最重的组件 |
| ClickHouse | 保留 | 合适 | 频道指标历史（曲线 + 跨频道排行）和运行统计都是它的强项。它要存补不回来的频道指标历史，所以必须有备份、写入积压告警，规模化时两副本 |
| MinIO | 保留 | 功能合适，上游已停止维护 | 仓库 2026-04 归档，不再有安全补丁和官方镜像。约定三条：只用标准 S3 功能；不直接暴露到外网；规模化或对外交付前再评估（备选 SeaweedFS 或有人维护的社区分支） |
| Prometheus / Alertmanager / Grafana | 保留 | 合适 | — |
| Loki + Alloy | 保留 | 合适 | 日志量用单实例就够 |
| KEDA | 去掉 | 产品可以，但用不上 | 装了从没用过；需要按积压扩缩时再装 |
| CDC 探测链路（`infra_smoke` 库 + `infra_outbox_slot` + 探测连接器） | 去掉 | — | 额外占一个复制槽（R9 积压到 1.3 GB）；去掉 Debezium 后没有意义 |
| infra-kafka-validation Pod | 去掉 | — | 只是执行 `sleep infinity` 的调试容器 |
| ingest（旧 HTTP 入库，0 副本） | 去掉 | — | R3 之后不用 |

## 4. 存储与保留规则

长期保留的只有三类：PG 当前资料（随频道数和新视频数增长）、ClickHouse 频道指标历史（只有播放量、粉丝量、视频总数三项，随时间增长）、ClickHouse 运行汇总；其余全部有固定期限。一千万频道持续更新时，MinIO 总量不到 1 TB，且基本不随时间增长。

**MinIO 保留规则**

采集单元抓取成功、解析成功、已写入 PG 后，MinIO 里的那份只是备用副本，短期保留即可。评论正文不进 PG，同样按 MinIO 规则删除。按"目录 + 生命周期规则"自动过期，不用清理程序逐个判断删除（千万级时每天上千万个对象，逐个删撑不住）。

| 目录 | 内容 | 保留 | 删除方式 |
| --- | --- | --- | --- |
| `raw/{平台}/{日期}/…` | 原始响应，zstd 压缩 | 2 天 | 生命周期自动过期 |
| `parsed/{平台}/{日期}/…` | 解析结果（含评论正文） | 2 天 | 生命周期自动过期 |
| `evidence/…` | 失败时复制进来的原件 | 问题解决前不删 | 问题解决后由清理程序删（量很小） |
| `samples/…` | 按频道哈希固定抽 0.1%～1% 的原件 | 30 天 | 生命周期自动过期 |
| `delivery/…` | 交付变更日志和快照 | 日志 14 天，快照留最近 2 份 | 生命周期自动过期 |

- 期限设 2 天而不是 1 天，是给解析、入库积压留余量；另加告警"解析或入库积压超过 12 小时"，告警时可临时调长。
- 抽样原件用于解析器的新旧对照回放和回归测试；其余解析 bug 超过 2 天才发现的，靠重新采集。
- 评论的影响：首次画像在同一计划内运行，2 天足够；定时重新画像间隔 60～365 天，只用当次更新新抓的评论，缺失的评论文件不报错（读取返回空值，Agent 照常运行）。若以后要用评论辅助训练，须在删除前另行导出。

**其他存储**

| 存储 | 增长来源 | 保留 / 上限 |
| --- | --- | --- |
| PG 当前资料 | 频道数 + 新视频数（视频列表只增不减） | 长期；流水表 30 天清理 |
| PG WAL / 复制槽 | 写入速度 | `max_slot_wal_keep_size` 上限 + 积压告警 |
| ClickHouse 频道指标历史 | 每次 ABOUT 更新一行（播放量、粉丝量、视频总数） | 长期，不删、不降采样 |
| ClickHouse 运行事件 | 请求、计划、失败等运行记录 | 明细 180 天，小时 / 天汇总长期 |
| Kafka | 消息量 | 3 天 |
| Loki / Prometheus | 日志、指标 | 7 天 |

**指标历史（10-14 定）**

只有频道的三项数值留历史：**播放量、粉丝量（订阅数）、视频总数**。每次 ABOUT 更新（频道资料时钟到期）写一行，长期保留在 ClickHouse 的"频道指标历史"表里。其余一律只存当前一份，不留历史。

| 数据 | 存哪里 | 历史 |
| --- | --- | --- |
| 频道播放量、粉丝量、视频总数 | 最新值在 PG；每次 ABOUT 更新在 ClickHouse 记一行 | 长期保留，不删、不降采样 |
| 频道其他资料（名称、简介、国家等） | PG 当前一份 | 不留 |
| 视频资料（标题、描述、标签、发布时间、时长等） | PG 当前一份；首次采集的视频和之后新增的视频全部保存 | 不留 |
| 视频播放、点赞、评论数 | PG 当前一份，复采时覆盖成最新值 | 不留 |

- 为什么放 ClickHouse（10-14 讨论确定）：既要看单个频道的增长曲线，也要做跨频道排行和分布统计（如"近 30 天涨粉最快的频道"），跨频道扫描正是 ClickHouse 的强项；列式压缩后每年约 10～20 GB，放 PG 约 140 GB（含索引），会让 PG 更早碰到分库线。
- 表设计：平台、频道 ID、观测时间、播放量、粉丝量、视频总数。同一频道同一观测时间只留一行，重试不会产生重复；按"平台、频道 ID、观测时间"排序，画单个频道的曲线快。另建一张"每频道每天最后一个值"的日汇总表，排行和区间对比直接查它。
- 这份数据补不回来（过去某天的粉丝数无法再抓到），所以 ClickHouse 的可靠性要求随之提高：定期备份（clickhouse-backup，目标和 PG 一样可配置，先放集群内 MinIO，以后改云备份）；ClickHouse 写入程序积压超过 12 小时告警，保证在 Kafka 3 天保留期内发现；规模化时两副本。
- 交付：每次观测都交付一条，业务库自己也存一份历史。业务方用 ClickHouse 存更合理（他们同样要做曲线和排行）；交付文件是 JSONL + zstd，ClickHouse 可以直接从对象存储读这种文件，业务方的入库可以很简单。视频的最新数值照常随更新交付，业务库按"观测时间新的覆盖旧的"更新。
- 现状要改：这些数值现在写在运行事件表 `crawl.events` 里，和运行事件同一条 180 天删除规则（`database/clickhouse/r5.sql:6`），频道历史查询还限制最多 1,000 个点（`apps/control-api/src/analytics.ts:54-58`）。要把频道三项拆进专用表、去掉删除规则、搬过已有数据；运行事件里不再带视频数值。
- 体量（L1 一千万频道）：每天约 100～300 万行，压缩后每年约 10～20 GB。按时间线性增长是业务要求的结果，属于预期内的增长。

**容量估算（L1 一千万频道、每天约 300 万次更新；量级估算，不是承诺）**

| 存储 | 估算 |
| --- | --- |
| MinIO raw（压缩后，2 天） | 约 200 GB |
| MinIO parsed（2 天） | 约 60 GB |
| MinIO delivery（日志 14 天 + 2 份快照） | 约 125 GB |
| PG 采集数据 | 首次约 300 GB（每频道约 30 个视频，共约 3 亿行）；之后随新视频增长，按 3 成频道活跃、每个活跃频道每年约 100 个新视频估算，每年约 +300 GB |
| ClickHouse 频道指标历史 | 每年约 10～20 GB（压缩后） |
| Kafka | 每个 broker 几十 GB |

当前需补的漏洞：失败原件解决后从不删除（R3）；清理筛选随历史线性变慢（R7，改成生命周期后自然消失）；PG 和 ClickHouse 缺容量告警。

## 5. 下发设计

采集系统只生产一份有序的变更日志和定期全量快照，放在 MinIO；每个业务库用 S3 只读账号自己拉取、自己记游标。业务库从 1 个变成 10 个，采集系统的成本和存储不变。

**链路（10-14 已定：JDBC Source + S3 Sink，两个都是现成的开源插件；去掉 Debezium，不写代码）**

1. 定稿事务：更新采集 PG 当前资料，同一事务写 outbox。
2. JDBC Source 连接器每 5 秒查一次 outbox，把新行发到 Kafka `delivery.entity`（频道、视频、画像、下线；64 个分区，按频道分区）。配置要点：`mode=timestamp+incrementing`（按写入时间 + 自增 ID 记读取位置）；`timestamp.delay.interval.ms=30000`（只取 30 秒前写入的行，避开"事务提交顺序和 ID 顺序不一致"导致漏行，我们的事务最长 10 秒）；用 Kafka Connect 自带的转换把消息 key 设为频道 ID，保证同一频道进同一分区。outbox 表按天分区，3 天前的分区直接删除。
3. 指标不经过 PG outbox（避免每天几千万行写进 PG）：解析程序把可交付的观测（已纳管频道的）按 `delivery.v1` 指标格式另发到 Kafka `delivery.metrics`，S3 Sink 订阅它。不能让 S3 Sink 直接订阅 `facts.observation`：那里还有搜索候选判门槛时采到的数据，而候选不交付（10-09 定）。
4. S3 Sink 连接器（插件，跑在现有 Kafka Connect 里）：每 5 分钟或攒够 1 万条写一个文件，zstd 压缩，文件名 `delivery/{主题}/{分区}/{起始偏移量}.jsonl.zst`，保留 14 天。
5. 每周快照：定时任务从 PG 备库按分区导出当前状态；开始前记下各分区偏移量，写进快照说明。
6. 业务库按分区、按偏移量顺序应用，游标和数据在自己库里同一事务提交；可选地把游标回报给采集系统，用于显示落后程度和告警。

**记录格式**：采集系统自己的通用合同 `delivery.v1`，记录分两种。① **当前状态记录**：频道、视频、画像、下线四类，每条 = `(平台, 实体ID, 版本号)` + 该实体的完整当前状态，不是字段级差量；业务库只按一条规则应用：版本号更大才覆盖。② **观测记录**：频道的播放量、粉丝量、视频总数，每次 ABOUT 更新一条，按 `(平台, 频道 ID, 观测时间)` 去重后**追加**，用来保存历史；视频的播放、点赞、评论数也以观测记录交付，但业务库按观测时间新的覆盖旧的，只留最新值。两种记录都不含评论正文和采集内部字段；旧业务库结构的映射由业务侧完成，`legacy-publication` 作为参考实现交给业务方。

**图 5 一份日志、各自的游标：快照 + 日志 + 游标**

```
Kafka delivery.* 分区 p0（按频道哈希；p1…p63 同理）

  偏移量 ──────────────────────────────────────────────────────────────►
  文件    [0 ～ 9,999]   [10,000 ～ 19,999]   [20,000 ～ 29,999]   [30,000 ～ …]
          （每 5 分钟或 1 万条一个文件，保留 14 天，之后自动删除）
                                 ▲                    ▲
                                 │                    │
  每周快照 S ────────────────────┘                    │
    （快照记下"p0 从 12,000 起"）                     │
  业务库 A 的游标：p0 = 23,000 ───────────────────────┘ 游标：从这里继续读

  新接入的业务库：先加载快照 S → 从 p0 = 12,000 开始读日志
                  （与快照重叠的部分：版本号更大才覆盖，重复应用不出错）
  落后超过 14 天：日志已删 → 重新加载最新快照
```

**各种情况怎么处理**

| 情况 | 业务库怎么做 |
| --- | --- |
| 新业务库接入 | 加载最近一份快照，再从快照记下的偏移量读日志；重叠部分因版本规则无害 |
| 正常运行 | 每 5 分钟左右拉新文件，按偏移量应用 |
| 停机几天后恢复 | 从自己的游标续读，14 天内都能补上 |
| 落后超过 14 天 | 重新加载快照再接日志；采集系统不为落后的库无限保留日志 |
| 数据出错要重建 | 同上，用快照重建 |
| 新业务库要以前的指标历史 | 快照只含当前状态、日志只有 14 天；更早的频道指标历史由采集系统从 ClickHouse 一次性导出给它 |
| 只要部分数据（某平台、某层） | 先读全量日志自行过滤；需求多了再由采集系统派生专门的订阅流 |
| 格式升级 | 新增可选字段兼容直接用；不兼容改动发 `v2`，与 `v1` 并行一段时间 |

**为什么不让业务库直接消费 Kafka**：每个外部业务库都要接入采集集群的 Kafka，与"业务库单独部署"的边界冲突；用压缩主题做快照又要在 Kafka 里长期存一份完整当前数据（三副本几百 GB）。

**S3 Sink 选择**：[Aiven S3 Sink](https://aiven.io/docs/products/kafka/kafka-connect/howto/s3-sink-connector-aiven)（Apache-2.0，支持 zstd、按"主题-分区-起始偏移量"命名、支持 S3 兼容存储；仓库已改名为 `Aiven-Open/cloud-storage-connectors-for-apache-kafka`，v3.4.3 于 2026-09-08 发布）。Confluent S3 Sink 用 [Confluent Community License](https://www.confluent.io/en-gb/confluent-community-license-faq/)，内部使用不受限，但不需要。

**为什么去掉 Debezium、用 JDBC Source**：S3 Sink 只能读 Kafka，读不了 PG，所以 outbox 到 Kafka 这一段必须有组件做。交付是批量的，用不上 CDC 的秒级实时；而 CDC 要占复制槽，过去两次事故（09-23 复制槽作废、10-13 WAL 堆积）都出在这里。JDBC Source 是 Kafka Connect 生态里现成的"按间隔查表"连接器，不占复制槽，PG 主备切换时照常连新主库，和 S3 Sink 跑在同一个 Kafka Connect 里。代价是几秒到几十秒的延迟和每 5 秒一次的小查询，对 5 分钟一批的交付没有影响。Confluent 的 JDBC 连接器功能相同，但用的是 Confluent Community License，选 Aiven 开源版即可。

**量（L1 一千万频道）**：每天有变化的频道约 100～300 万；频道 / 视频 / 画像记录压缩后每天约 1.5 GB，指标记录压缩后约 0.3 GB；一份全量快照压缩后约 50 GB。

接收侧的 business-sink、逐条回执 delivery-receipts、业务库本身都移出采集系统。

## 6. 多平台设计

平台无关的骨架只做一套，每个平台只写适配器；现在的表、接口契约和 Kafka 主题里都还没有"平台"维度（频道 ID 默认是 YouTube 的 `UC…`），这是第一批要补的。

**图 6 多平台：骨架一套，适配器每平台一套**

```
平台适配器：每个平台各写一套（新增平台只加这一层）
┌────────────────┬────────────────┬────────────────┬────────────────┐
│ YouTube        │ TikTok         │ Instagram      │ …              │
│ 抓取步骤       │ 抓取步骤       │ …              │                │
│ 解析器         │ 解析器         │                │                │
│ 会话 / 指纹    │ 会话 / 指纹    │                │                │
│ 代理池与计分   │ 代理池与计分   │                │                │
│ Worker 组      │ Worker 组      │                │                │
└────────────────┴────────────────┴────────────────┴────────────────┘
         ▼                ▼                ▼                ▼          通用事实（带平台字段和 schema 版本）
┌─ 平台无关骨架：只做一套 ──────────────────────────────────────────┐
│ 统一身份 (platform, 平台内ID) → 内部 ID                           │
│ 调度 · 三个时钟框架 · L0 / L1 分层                                │
│ MinIO 目录规则 · Kafka 通用事实主题 · 入库 · ClickHouse           │
│ 交付 delivery.v1 · 控制台 · 告警                                  │
└───────────────────────────────────────────────────────────────────┘
```

| 平台无关，所有平台共用 | 每个平台各写一份适配器 |
| --- | --- |
| 统一身份：`(platform, 平台内ID)` → 内部 ID | 抓取步骤（YouTube 按旧系统规则） |
| 调度、三个时钟的框架、L0 / L1 分层 | 解析器：平台原件 → 通用事实 |
| MinIO 目录规则 `raw/{platform}/…` | 会话、指纹、限流规则 |
| Kafka 通用事实主题（带平台字段和 schema 版本）；原件主题按平台分开 | 代理池与计分规则（各平台封禁方式不同） |
| 入库、交付、ClickHouse、控制台、告警 | 平台特有字段（作为通用 schema 的扩展字段） |
| 通用数据模型：账号、内容、指标观测、画像 | Worker 部署与 Temporal Task Queue，按平台分开扩缩 |

- 跨平台识别同一个创作者（同一人的 YouTube 号和 TikTok 号）以后再做，但内部 ID 从现在起就与平台 ID 分开。
- 新增一个平台的标准工作 = 适配器 + 解析器 + 代理池 + 一组 Worker；骨架不改。

## 7. 亿级扩展设计

决定成本的主数是"每天请求数"：分层后约每天 1,000 万次（平均每秒 120 次），不分层则约 7,000 万次。管道各段都可以加机器扩；吞吐的硬上限是代理，不是架构。

```
每天请求数 = Σ（各层）频道数 × 每天更新次数 × 每次更新请求数
```

| 环节 | 现在 | 到千万 / 亿级的问题 | 设计 | 何时做 |
| --- | --- | --- | --- | --- |
| 调度 | 每 30 秒扫时钟表 | 亿级表不能全表扫 | 到期时间按小时分桶成队列；调度器按频道哈希分片多副本 | 现在定设计 |
| Temporal | 一个频道计划一个工作流 | 每秒上百次启动，持久化压力大 | 一个工作流处理一批频道（100～500 个，每天约 1.5 万个工作流）；独立 PG；按平台 / 角色分 Task Queue。history shard 512 已够用 | 千万级之前 |
| Kafka | 每个主题 3 个分区 | 每个主题最多 3 个消费者并行 | 预设 64～128 个分区；按频道分区的主题后加分区会打乱顺序，趁数据少一次定好 | 现在 |
| MinIO | a1 单节点，上游已停止维护 | 每天百 GB 级写入 | 原件 zstd 压缩；2 天自动过期；规模化前重新评估（MinIO 多节点或 SeaweedFS） | 百万级之前 |
| PG | 一个集群放 5 类用途 | 视频列表只增不减，3 亿行起步、每年约 +3 亿行 | 采集 PG 独立（第 8 节）；采集数据按频道哈希分区；超过 1～2 TB 时按频道分到多个 CNPG 集群（应用层分库，不上 Citus） | 拆分现在做，分片以后 |
| ClickHouse | 单实例，指标历史混在运行事件表里 | 频道指标历史每年约 4～10 亿行、长期保留 | 频道指标历史拆专用表；分片 + 副本集群；磁盘按每年约 20 GB 增长规划 | 拆表现在做，集群千万级之前 |
| Agent | 单线程、不组批 | 千万纳管频道：每个新纳管频道都要画像，之后每 60～365 天重画 | 组批推理、多副本，必要时 GPU | 纳管频道过百万之前 |
| 解析 / 入库 | 无状态单副本 | — | 加副本即可，上限是分区数 | 按积压扩 |
| 代理 | 免费公共源，健康约 40 个 | 需要上千个健康代理 | 稳定付费来源，按平台、按国家分池 | 规模化之前（待定） |

**现在就要定、以后很难改的六件事**

1. 身份带平台维度：所有表、主题、对象路径的主键带 `platform`。
2. "频道"是唯一分区键：Kafka key、PG 哈希分区、MinIO 前缀、ClickHouse 排序键、交付分区都用它；不写跨频道事务。
3. Kafka 分区数一次定到位。
4. 分层模型：L0 / L1 各自的目标数量和更新频率。
5. 调度改成分桶的到期队列。
6. PG 按用途拆开；采集数据先做哈希分区。


**图 7 频道是贯穿所有组件的唯一分区键**

```
频道身份 (platform, channel_id) ──哈希──► 分片号 k
   │
   ├─► 调度    ：分片 k 归某一个调度副本，到期队列按小时分桶
   ├─► Kafka   ：分区 = k，同一频道的消息永远有序
   ├─► MinIO   ：raw/{platform}/{日期}/{k}/…
   ├─► PG      ：按 k 哈希分区；超过 1～2 TB 时按 k 分到多个 CNPG 集群（应用层分库）
   ├─► ClickHouse：ORDER BY (platform, channel_id, 时间)
   └─► 交付    ：delivery 分区 = k，业务库按分区并行应用

规则：不写跨频道的事务。分片只是加机器，不用改代码。
```

重建后的收益：给 Temporal 留的 45 个连接（共 100）全部归采集；采集 PG 不再有复制槽；业务库问题（如 R14）不会再拖累采集主库；库名、表结构、主题分区一开始就是新设计，不带历史包袱。

**重建步骤（10-14 定：只保留底座，旧数据全部删除，代码保留）**

保留的底座：K3s 和各个 Operator、cert-manager、监控与告警、Kafka 集群、MinIO 服务、ClickHouse 服务、Temporal 服务、Kafka Connect。

1. 先完成代码：阶段一（按旧规则修正采集）和阶段二（平台维度、新表结构、交付链路）的代码在测试 PG 上验证通过。
2. 把要留下的设置导出成代码仓库里的种子文件（待确认）：搜索词、集中配置、代理来源。管理员账号重建时重新创建；加密浏览器身份删除后由指纹网关重新生成。
3. 删除前留一份全量备份（建议，约 5 GB），保留两周，以防需要对照或找回设置。
4. 暂停自动流程，停掉全部采集程序。
5. 删除：采集 PG 上的全部库、Kafka 业务主题、ClickHouse 业务表、MinIO 业务数据；卸载 Debezium、CDC 探测、KEDA、调试 Pod、旧 ingest、business-sink、delivery-receipts。
6. 新建：crawler-pg 正式库（新结构）、temporal-pg、64 分区的 Kafka 主题、ClickHouse 新表（频道指标历史、运行事件）、MinIO 目录与生命周期、JDBC Source + S3 Sink；导入种子文件。
7. 部署新代码，先用少量真实频道做全量和更新验收，再打开自动搜索、准入和定时更新。

**单副本怎么处理**：不是每个组件都要多副本。原件丢了可以重抓，Temporal 停了只是暂停。真正不能丢的是 PG 当前资料、ClickHouse 频道指标历史和交付日志：PG 配 PITR，ClickHouse 定期备份，其余按 RPO / RTO 逐项定。PITR 的备份目标做成可配置：现在指向集群内 MinIO 的 `crawl-pg-backup` 桶（只防单台机器坏），以后买云备份时改地址和密钥即可；在那之前"整组机器丢失无法恢复"是已接受的风险。

## 9. 八项质量的保障手段与当前差距

架构上八项都有对应手段；差距主要在部署（单副本、备份）、代理来源和度量。编号对应推进计划 §7 差距清单。

| 质量 | 靠什么保证 | 当前差距 |
| --- | --- | --- |
| 高性能 | 抓取不等数据库，全程异步；入库端批量写；统计走 ClickHouse | 无分阶段 P95；未装 pg_stat_statements；control-api 连接池为 1（C4） |
| 高并发 | 并发 = 可用代理数 × 每代理并发，与 Pod 数无关 | 总并发 3（C2）；健康代理约 40 个（C3） |
| 高可伸缩 | Worker、解析、入库无状态，按频道分区，加副本即扩；调度分片；PG 可分片 | Kafka 3 分区；调度扫表；无平台维度 |
| 高可靠 | 每段可重做：MinIO 固定文件名、Kafka 至少一次 + 按 ID 覆盖、入库账本对账、Temporal 持久执行、PG 同步复制、交付按版本幂等 | 单副本多（R13）；PG 无 PITR（R2，备份目标先用集群内 MinIO）；ClickHouse 单实例无备份，而它要存补不回来的频道指标历史；MinIO 无备份（R1）；无异地备份（以后买云备份）；两个已确认缺陷（R5、R6） |
| 高安全 | 采集节点无数据库账号；MinIO / Kafka 按服务分账号；业务方 S3 只读；NetworkPolicy 默认拒绝；WireGuard + TLS | 控制台走临时隧道无访问控制；待换密码；未做镜像扫描（S1） |
| 高可观测 | Prometheus（积压、吞吐、容量）+ Loki + ClickHouse 业务事件；平台 + 频道 + 计划 + 文件 + 链路 ID 串联；业务库落后程度 | 积压告警待授权（C1）；告警无处理责任人（O1） |
| 易用 | 控制台按"PG 管操作、ClickHouse 管趋势"分工；中文口径统一 | U1 / U2 进行中 |
| 可维护 | 一组件一职责；单仓、单镜像多入口；契约集中；平台适配器隔离 | 生产沿用 test / preview 命名（O2）；CI 未跑通（M1） |
| 存储不快速增长 | 长期只有 PG 当前资料、ClickHouse 频道指标历史和运行汇总；其余全部有期限 | 失败原件不删（R3）；指标历史 180 天后会被删（混在运行事件表里）；业务库历史表无保留期（R15，移出后归业务侧） |

## 10. 实施路线

按"数据正确 → 打地基 → 数据安全 → 产能 → 规模化"五个阶段推进，每个阶段过关卡才进入下一阶段。当前在阶段一。

**图 10 实施路线：5 个阶段、4 个关卡**

```
┌─ 阶段一 数据正确（进行中） ──────────────────────────────────────────┐
│ 按旧采集规则逐条移植：会话语言、评论、直播、国家码、上传列表、休眠   │
│ 用真实原件新旧对照回放验证；旧数据不更正，重建后重新采集             │
└──────────────────────────────────────────────────────────────────────┘
        │

┌─ 阶段二 打地基 + 重建 ───────────────────────────────────────────────┐
│ 代码：平台维度、Kafka 64–128 分区、频道指标历史专用表                │
│ 交付：JDBC Source + S3 Sink + delivery.v1 + 周快照                   │
│ 重建：保留底座，删除全部旧数据，新建采集库、Temporal 库、主题、表    │

        ▼
┌─ 阶段三 数据安全 ────────────────────────────────────────────────────┐
│ PG PITR + ClickHouse 备份：目标可配，先放 MinIO，以后改云备份        │
│ 失败证据清理；解析 / 入库积压告警（R1–R7）；按 RPO / RTO 定多副本    │
└──────────────────────────────────────────────────────────────────────┘
        │
        ◇ 关卡：从零恢复演练达到约定的 RPO / RTO

┌─ 阶段四 产能 ────────────────────────────────────────────────────────┐
│ 分桶调度多副本、批量工作流、Worker 并发、Agent 组批（C1–C5）         │

└──────────────────────────────────────────────────────────────────────┘
        │
        ◇ 关卡：按目标请求量连续运行不积压
        ▼

阶段二的代码可以和阶段一并行写；重建在两者代码都完成后一次性进行，之后用新代码重新采集。页面加强（U1 / U2）和控制台访问控制（S1）贯穿各阶段。每项部署后在真实频道上验证。
