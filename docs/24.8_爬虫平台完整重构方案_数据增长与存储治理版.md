### 0.2 不再反复改变的选择

- 保留 Temporal、Kubernetes、KEDA/HPA、Data Ingestor、PgBouncer、Crawler PostgreSQL HA、Kafka/Debezium、ClickHouse、对象存储和业务控制台。
- Kafka 仅承担 `publication.outbox → Debezium → Kafka → Business Consumer` 的跨系统分发；历史分析使用独立可靠投递链，不把所有任务、结果和日志总线化。
- 删除中央实时 Rota。中心 Proxy Control 管库存、分组、服务器绑定和策略；每台采集服务器一个 Node-local Proxy Manager 管实时选择、并发、健康、冷却和本地会话。
- 一台服务器可以混跑多个种类、多个实例的 Worker。Server、Pod、进程、执行槽和 HTTP 并发不是同一对象。
- 不自研 TLS、加密算法、证书轮换器、通用网络 ACL 或第二套任务队列。基础设施安全交成熟组件，业务代码负责对象级授权、代次、幂等和版本。
- 不新建独立 Finalize Worker。领域证明和 `trySettlePlan(tx, plan_id)` 保留；不是取消完整性校验。
- 不因为未来可能增长就预建 Citus／应用分片；也不承诺单 PostgreSQL Primary 无限写入。

## 2. 四支柱与正确的业务链路

四大职责为：任务派发、网络采集、入库更新、计算分发。它们是逻辑边界，不是一职责一台服务器。

```text
控制：Query Clock／频道三 Clock → Planner／PlanStore → 持久启动意图 → Temporal

首次采集：QueryRun → 候选频道 → 准入 → Full Plan
                                      ├─ 主线：About → Uploads／冻结目标 → Detail
                                      │                             └─ 必要时 Data API → 原阶段恢复
                                      └─ Agent 支路（输入契约允许时并行）

持续更新：About／Video／Agent 到期 → 一个冻结 Refresh Plan
                                      ├─ About／Video 所需主线
                                      │        └─ 条件 Data API → 原阶段恢复
                                      └─ 所需 Agent 支路（Agent-only 不启动采集主线）

各支路独立提交 → Data Ingestor → 事实／检查点／领域证明／可靠义务
                                  └─ 同事务 trySettlePlan；必要 Feature 回执后再复核

PG 当前事实 → Business Console 当前视图
            ├─ 独立分析义务 → 有界批投递 → ClickHouse 历史视图
            └─ 已批准发布的不可变事件 → publication.outbox → Debezium → Kafka
                                                                   → Business Consumer → Business DB
```

Full 不是永远扫描一个频道全部历史；更新频道不是 Full 后面的固定串行步骤；Agent 不是必须等视频全抓完才启动；Data API 不是所有请求必经节点。Channel Current 可以随合法批次应用而更新，不必等待整轮计划结束；“当前数据可用”和“本轮完成”分别判定。

## 3. 模块、成熟组件与部署职责

| 模块 | 使用什么 | 项目需要实现的内容 | 不自研的内容 |
|---|---|---|---|
| Control App | 模块化应用＋PG Store | Query／准入／计划／Clock／命令API；可分别配置后台执行池 | 第二套通用 Workflow 引擎 |

| 分发 | Outbox＋Debezium＋Kafka | 发布数据契约、业务计算、Inbox和交付确认 | 自研消息Broker／双写补偿总线 |

| 对象 | S3兼容接口；沿用已选实现或现成服务 | 不可变引用、校验、保留、GC | 对象存储协议 |
| 网络安全 | 支持策略的CNI、标准TLS、成熟证书管理 | 配置、接入标准验证库、业务授权 | 加密算法、证书签发协议、ACL引擎 |
| 观测 | Prometheus/Grafana/Alertmanager、OTel、既有日志后端 | 埋点、业务事件、错误关联、仪表板 | 并行建设多套通用日志/Trace平台 |

Data Ingestor 的接收与 Fast Apply 首期放在同一服务边界，内部按模块隔离。大量事实写入不绕业务控制API。Feature、Projection、Read Model 在代码中有独立预算和接口，但不因表数量拆微服务；确有资源争用时可用同镜像的独立执行模式部署。

Temporal、Crawler PG、Kafka、ClickHouse、对象存储都有自身状态与运维责任；“业务只有四步”不表示基础设施无需备份、监控和升级。当前选型由本项目需求决定，不宣称所有同规模系统都必须采用相同组件。

## 4. 身份、版本与完成语义

| 身份 | 作用 | 重试约束 |
|---|---|---|
| query_binding_id | QueryTerm＋国家＋业务分类的长期绑定 | 多来源合并，不因为重试复制Binding |
| query_run_id | 一轮冻结搜索与continuation | 重试不换参数或Run |
| channel_id／plan_id | 长期频道／本轮Full或Refresh | 一个频道可有多轮计划，统计不可混用 |
| logical_batch_key | 本轮冻结的逻辑批次 | 相同业务单元的普通重试保留 |
| submission_id＋payload_hash | 一份不可变采集结果 | 原字节重传；同ID异Hash拒绝 |
| execution_epoch／domain_generation | 写入权与领域代次 | 合法接管才更新，不用重试洗掉旧身份 |
| request_id／batch_id | API或Agent单项义务／物理组批 | 重组可换batch，已存在单项request不换 |
| source_revision／event_id | 发布版本与事件身份 | 顺序／幂等分别校验 |
| server_id／worker_instance_id／node_boot_id | 服务器、执行实例、重启代次 | 容器重建不是同一进程，仍可恢复同业务Plan |
| assignment_generation | IP资源分配版本 | 不替代任务写入授权，也不能远程撤销已泄露凭据 |

必须区分：

```text
captured          = 网络结果已捕获，未必业务可用
RECEIVED          = 中央已耐久接管该Submission的恢复责任
APPLIED           = 对应逻辑批次的事实与回执已提交
Domain Settled    = 本域形成允许的终结结果，未必是完整成功
Plan Settled      = 本轮required domains按政策结束，未必所有域成功
Publication Ready = 指定版本满足发布合同
DELIVERED         = 外部业务本地事务已接受，有可核对回执
```

Fast Apply 可直接返回 APPLIED；不强制在 UI 上停留一次 RECEIVED。一个频道的 10 个 Submission APPLIED 不等于 10 个完整频道。所需工作尚未枚举／封口时，`pending=0` 不证明完成。

### 4.1 Temporal载荷与历史预算

只传有界标量／小集合／冻结引用，不把大目标列表、Raw或异常堆栈无限塞入Workflow输入、Activity结果、Signal或Heartbeat。以实际部署版本的Payload/历史大小限制设置更低的应用预算，入参和出参都测序列化字节。自建默认限制可以配置，不能把调高限制代替有界设计。[O20]

引用必须指向持久、版本化、可校验的目标清单，不只指向原Worker内存或易失缓存。长流程保持有限Run；接近历史预算时通过受控后继流程/Continue-As-New等SDK机制处理，并保留原业务身份与待办，不在无限历史中堆每次HTTP事件。

## 5. Discover、Query 与固定业务分类

### 5.1 自发现闭环

```text
种子／频道／视频／Agent信号
→ Query Candidate
→ 规范化、来源去重、国家与业务分类、准入
→ QueryBinding
→ Query Clock 到期 → 冻结 QueryRun → Discover
→ 候选频道 → 归并／资格／Full＋Agent
→ 已确认频道／视频事实产生可靠 Query 派生义务 → 回到候选Query
```

事实成功提交与 Query 派生义务必须处在可恢复边界内，不能事实已入库、进程崩溃后永久丢掉新 Query。派生工作可以异步，不持核心事务进行昂贵文本／模型计算。

### 5.2 Query Clock

首次 Run 用 `THIS_YEAR`；成功后规则输出离散 `WEEK` 或 `MONTH`，生成下周／下月的 `next_run_at` 与 `THIS_WEEK`／`THIS_MONTH`。不增加连续质量评分系统。低价值状态为 `COOLDOWN`／`DORMANT`，人工停用为 `DISABLED`，初始为 `BOOTSTRAP`。

规范字段包括 `last_success_at`、`next_run_at`、`refresh_factor`、`policy_version`；失败重试有独立 retry 时间，不能反复产生新的正常周期。月度计算必须配置时区与月底处理规则，不把自然月与固定30天混用。一个QueryRun的窗口、sort、locale、国家和分类版本冻结。

`THIS_WEEK` 的业务意图沿用“最近一周”，但公开搜索结果不是完备增量日志。真实 Adapter 的过滤边界、分页限制、索引延迟需要集成测试。延迟执行显示 `coverage_gap`／窗口风险，由已批准策略或人工回补处理；**本版不默默改成另一套自动 Year/Month/Week 算法，也不承诺不漏整个站点。**

## 8. API／Agent组批、结果返回与重试

Agent保留用户确认的**每批30条基准**，但30不是并发数、不是服务器数。满批、尾批、等待期限、最大在途批数必须通过配置冻结与验收。API按端点、字段／评论需求、凭据配额域等组批，不把某个端点上限套到所有调用。

```text
父计划产生单项request → 持久请求账本
→ 兼容组批 → 冻结batch manifest
→ 事务外调用外部API/模型
→ 按request_id逐项校验（不按数组位置猜频道）
→ Data Ingestor原子保存结果／失败／回执
→ 原计划读取同一request结果
→ 原域继续验证、恢复与封口
```

API返回成功不代表VIDEO成功；Agent的旧input_revision只能满足合法原义务。已成功项不因同批一个失败而再次计算。外部服务没有幂等或结果查询能力时，超时重试可能重复收费，数据库幂等不保证外部调用恰好一次。

恢复责任分开：HTTP局部重试、会话恢复、API调用、Agent调用、Submission重传、短事务重试、工作阶段恢复分别有预算。计费attempt按真实外部调用累加，不能层层重置。HTTP 429／配额等待不是代码Bug的充分证据。

## 9. Data Ingestor与事务边界

### 9.1 “做薄”不等于只验JSON

只保留一个可靠写入边界：认证、版本／身份／Hash、授权、字段证据、有界Apply、回执及背压。它调用领域Store完成复杂业务校验，但不加 `Gateway → 内部HTTP → Apply服务` 的无意义转发。

Collector无Crawler PG凭据；读取冻结任务输入通过受控接口／不可变引用，结果统一进入Ingest。数据库连接、Schema、锁和事务实现不散落在远端脚本。

### 9.2 原子边界

| 边界 | 同一事务内 | 留在事务外 |
|---|---|---|
| T1 准入 | 幂等业务意图、Plan/Run、执行代次、所需依赖、启动意图 | Temporal调用、网络采集 |
| T2 接收 | Submission身份、实际可恢复载荷／受保护对象引用、RECEIVED | 大对象上传、耗时校验／解压 |
| T3 应用 | 授权与版本复核、事实、检查点／ledger、APPLIED、必要可靠义务 | YouTube／模型／Kafka调用 |
| T4 结算 | 小型领域证明、封口、Plan结果与合法发布义务 | 独立Finalize队列、全历史扫描 |
| Feature | Inbox、序号、Feature、Clock和继续处理义务 | 无界Gap追赶、网络调用 |
| Business接受 | Inbox、业务投影、可核对接受结果与回传义务 | 回Crawler通知 |

T2/T3可合并成Fast Apply直接返回APPLIED。中央暂不能Apply但要先接管时，必须实际耐久保存可恢复内容后返回RECEIVED；Hash或内存队列不是耐久载荷。

### 9.3 原子收口

所有可能改变本轮义务的路径遵守统一频道／Plan锁序。Store更新领域证明时，同一事务调用 `trySettlePlan`；必要Feature后到时也按同一锁序重检。先证明工作已枚举封口，再查未决义务；不能“两个支路各自看到另一方没完成，提交后再也没人结算”。

SQL冲突只重试整个短事务，不重采网络结果。COMMIT响应丢失先核对同业务身份；同ID同Hash返回原回执，同ID异Hash隔离。一条新Submission不必然获得新的合法业务写权。

**24.8写入约束：**Current去重、无变化字段跳写与历史字段白名单由Store/分析合同统一实施，不让每个Worker自行决定删掉必要证据。接收载荷、权威字段、回执和Trace按第16章共享引用与独立期限；Fast Apply无需为了凑流程同时永久保留一份“RECEIVED完整payload”和另一份相同“APPLIED完整payload”。

## 10. 代理资源：中心管理、本地执行

### 10.1 中央Proxy Control

业务控制台管理代理库存、供应商、国家、分组、绑定服务器、策略和凭据引用。`proxy_endpoint_id` 与实际出口 `egress_ip` 分开：旋转代理端点不等于固定独占IP。需要固定出口的会话保留实际路由和会话证据，不用库存条数推断可用并发。

中心批量下发Desired Assignment，本地批量上报Observed State。中心不参与每次请求申请。失联显示 `STALE/UNKNOWN`，不是“健康”或“可以立即把资源重复分出去”。

### 10.2 本地管理者

每个采集节点一个Node-local Proxy Manager，可按DaemonSet部署。它管理本机所有Worker共享的per-proxy并发、冷却、健康、会话及本地失败分类；不允许每个Pod各维护一份互不知情的可用额度。

不同Pod不共享localhost。选择并验收一种节点本地访问方式：受限Unix Socket挂载、受控node-local endpoint，或同Pod sidecar的明确部署。采用DaemonSet时不能把 `localhost` 当成跨Pod服务发现。不要把hostNetwork和特权权限作为默认捷径。

用户提及的“crawlle／类似resin”尚无确切实现版本和仓库定案，本版只冻结本地管理接口，不把未经核实的名称视为已经集成的依赖。不得因此引入第二套中央代理调度器。

补充检索发现 Crawlee SessionPool 与 `Resinat/Resin` 是可调查的会话／代理能力来源，但并未确认就是用户所指实现，也未审计其接口、安全或性能；不能把项目README中的吞吐宣传当本平台压测结果。后续仅在版本、接口和退出/租约语义验证后选择其中适合的能力，不同时叠加两套相互冲突的代理生命周期管理。[O21][O22]

### 10.3 心跳合同

```text
server_id / node_boot_id / report_sequence
assignment_generation / desired_policy_version / applied_policy_version
observed_at / last_success_at / agent_health
proxy_summary / changed_proxy_states[] / counter_deltas
```

报告序号、重启代次与去重防止重复统计；全量快照分页、有界，不因IP很多一次发巨型心跳。代理凭据不进心跳／日志／Trace；健康统计延迟单独展示。上报是观测，不能替代授权到期判断。**24.8：Current按身份更新，历史只保留关键状态变化与获准窗口汇总；禁止每次心跳永久追加全量IP快照，累计计数不能重复SUM。**详见16.6。

### 10.4 失联、重分配和真实撤销

本版新增防分裂约束：Assignment带代次及有限有效期；本地未能续到有效授权，到安全期限必须停用相关新请求。期间允许按剩余有效期运行，不能永久依赖旧配置。

迁移：中心记录新意图 → 旧节点停止使用并确认，或等待安全到期／执行供应商凭据撤销 → 新节点激活新代次。对外部代理供应商，中央数据库中的generation本身不能物理阻止旧节点已建立的连接。要求“绝不重叠使用”时，必须有可验证的撤销／出口隔离措施；否则明确不能承诺硬隔离。

只停止新请求不等于旧网络调用已经结束。关闭会话、取消传播、最大请求时长与迁移宽限要共同验证。代理授权代次和Plan写入代次分别执行，不能相互替代。

## 11. 服务器、Worker和快速加节点

服务器记录物理／虚拟资源、K8s Node、位置、版本、心跳和资源池。Worker记录实例、角色、Pod UID、server_id、build/version、Task Queue、执行槽与状态。

Kubernetes按资源requests进行调度，resources.limits不等于预留算力；节点无可分配资源时新增Pod可能保持Pending。[O19]

一台服务器可混跑Discover、Full、Update、Agent、API；数量只是示意，不给统一“每机多少Worker”的保证。模型本地推理、浏览器与普通HTTP采集的资源画像必须分开。

新采集节点接入：基础网络／身份 → 加入节点池 → 本地代理管理者就绪 → 有效代理分配 → Worker版本／Task Queue匹配 → 在额度内开始poll和网络操作。只有Pod Ready且实际能工作才计入容量，Pending不算。

Deployment总副本、每机布局和应用执行槽是三个配置层。按角色node labels、affinity／拓扑分布定义可调度范围，尽量不把任务永久绑定某台服务器。服务器移除流程先停新增、再有界排空、再撤销代理分配，不提供“随便拔机绝对不丢工作”的误导按钮。

## 12. 通信设计：稳定接口、复用与分段计时

### 12.1 生产通信合同

Worker→Ingest使用标准库，有界Submission和可复用连接。默认沿用已定gRPC/HTTP2；不自行实现加密、分帧重传或永久双向超级流。普通有界批量可用unary RPC；只有实际需要流式传输时使用有限生命周期Stream。协议变更需等价性和性能证据。

gRPC已建立的Stream不会因新Pod上线而自动重新分配，因此复用Channel、每批有限RPC与服务发现／负载策略需要一起验证。[O01][O02]

新Ingest实例实际接流，是扩容验收条件：比较实例间请求、字节、Apply数和队列年龄。可选已验证的客户端多端点负载或gRPC-aware L7入口，冻结一种主方案；不依赖普通L4转发使存量连接迁移。

### 12.2 严格区分通信时间与写库等待

```text
Worker侧：组包 → 序列化／压缩 → 等待发送额度 → RPC调用 → 等待回执
Ingest侧：入口排队 → 读载荷 → 解压／校验 → Apply准入 → 取连接
         → SQL／锁等待 → COMMIT／复制等待 → 回执发送
```

客户端“等待ACK”覆盖多个阶段，不能都叫网络延迟。标准库write返回也不证明服务端持久化；流控和应用有界内存是两层保护。[O02]

长时等待API／Agent释放采集执行槽，不占数据库事务；同一业务Plan可以等待，不要求一个CPU线程或代理会话一直占着。

### 12.3 资源上限

分别设置连接数、活动RPC、压缩／解压后字节、解码并发、等待Apply字节、Apply事务和Journal空间。必须考虑压缩比异常、巨大评论和最大条目；流控不能替代消息大小／解压后上限。

内网TLS/VPN的MTU、重传、CPU开销要测量；不能靠关闭加密换取验收通过。DNS缓存同时满足降压和及时发现新节点，禁止永久缓存旧endpoint。

## 13. PostgreSQL与PgBouncer：写入能力和并发预算

### 13.1 三种连接／并发不得混为一谈

```text
应用到PgBouncer的客户端连接
≠ PgBouncer到Primary的服务端连接
≠ 正在执行的事务／正在消耗CPU的查询
```

PgBouncer事务池在事务结束后复用后端连接；`default_pool_size` 等配置按数据库／用户等池边界生效。多个PgBouncer实例、额外用户／数据库池会扩大总预算，必须合并计算。[O03]

本版预算模型：

```text
客户端上限 ≥ Σ(最大同时存活实例_i × 每实例客户端池_i) + 维护预留
PG后端上限 ≥ Σ(各PgBouncer实例可能同时打开的后端池及reserve) + 直连服务 + 运维预留
活跃写事务预算 = 经代表性负载压测确认的安全并发，不等于max_connections
```

“最大同时存活”包含滚动发布surge和终止中仍持连接的旧Pod，不能只乘desired replicas。Temporal持久层、Feature、Console、分析投递、分发投影等若共享物理PG，也需计入物理资源预算；分schema不构成I/O隔离。

### 13.2 拒绝两个错误推论

- `cl_waiting`增加说明在等待服务端连接，不自动证明连接池设置太小；后端可能被长事务、锁、I/O或同步复制占住。
- PG CPU低不代表能增加并发；可能单核、锁、WAL或存储已经成为瓶颈。

先结合 `SHOW POOLS`／`SHOW STATS`、应用取连接耗时、SQL／COMMIT耗时和PG等待事件判断。[O04][O06][O07]

### 13.3 PG观察面

| 观察面 | 指标与证据 | 可能动作 |
|---|---|---|
| 应用排队 | Apply准入等待、连接获取等待、最老待Apply年龄 | 区分应用主动限流和PG阻塞 |
| 慢SQL | 归一SQLID、调用数、耗时、返回／影响行数、查询计划 | 优化已证实的访问路径，不盲目加索引 |
| 锁争用 | wait_event、阻塞链、事务年龄、热点channel／plan | 统一锁序、缩短事务、减少同频道重复工作 |
| WAL／提交 | WAL速率、write／sync、提交等待、复制反馈 | 核对存储与同步策略，不能静默降持久性 |
| I/O与内存 | 数据盘延迟、队列深度、缓存压力、checkpoint | 用持续负载而非瞬间带宽评估 |
| 空间与回收 | 可用字节、WAL/slot保留、dead tuples、vacuum进度 | 在触及危险线之前维护、归档或限新增 |

PG17的 `wal_sync_time` 是累计计时，用窗口增量除以同步次数增量才能得到该窗口平均值；统计重置、计时未启用和同步方法需处理。PG18将WAL I/O相关计时移到 `pg_stat_io`，Exporter要按实际版本映射。平均sync时间不冒充P95/P99。[O06][O07]

### 13.4 写入优化顺序

按证据评估：无效重复写／索引 → 有界批量 → SQL访问路径与锁序 → 事务长度 → 全局并发最佳点 → WAL／I/O／硬件。原生分区只对适合的表使用，不能因为行数大一律分区；分区不自动增加单主写能力。

增加Ingest副本可以增加解码能力，但不得自动放大PG总写并发。热频道的串行正确性边界不会因加机器消失；跨频道可并行，同频道不能乱序覆盖新版本。

<a id="chapter-14"></a>

## 14. 计算分发：Kafka保留，可靠性与计算版本分开

### 14.1 唯一分发主链

```text
可信Store确认版本满足发布政策
→ 同事务：发布版本/不可变输入 + publication.outbox
→ Debezium Outbox Event Router → Kafka
→ Business Consumer的业务Projection计算
→ Business本地事务：Inbox + 业务数据 + 接受回执/回传义务
→ Crawler交付确认接口 → DELIVERED投影
```

不使用24.5的Outbox轮询器作为并行生产分发方案，不让Worker直接PG＋Kafka双写。业务消费者不能只因Kafka offset已提交就标记Business写入成功。

### 14.2 计算输入必须可重现

本版沿用Consumer计算方案，但补充边界：Kafka事件携带最终有界业务payload，或**足够计算的不可变输入及引用**，包含source_revision、input_hash、schema_version、projection_policy/model版本。

只带 `channel_id + revision` 不足以重现被后续更新覆盖的数据。需要读Crawler时，通过受控只读接口读取该固定版本的有界manifest／快照，不在重放时读取latest Current再冒充旧revision。跨表一致输入必须有明确快照语义；不保持长数据库事务等待模型计算。

轻量、确定性的筛选可在发布前完成；耗时计算不放进采集写事务。不再另加一个必须运行的重计算平台：Consumer中的Projection模块即可。外部模型不确定／计费时，保存首次有效计算结果和调用身份，重复交付优先复用；不保证外部执行恰好一次。

### 14.3 Inbox和旧版本

业务事务中校验 `event_id + payload_hash`，同事件同内容幂等返回；同事件异内容隔离。按aggregate与发布序号阻止旧版本覆盖新版本。只有合同明确是完整最新态投影时才允许跳过被覆盖版本；增量Patch、删除／撤销和需要每个事件的流程不能任意合并。

源版本与算法版本分开。仅更换算法时必须形成新的合法发布／重算身份与排序规则，不能用旧source_revision静默覆盖。持久接受回执应有 `APPLIED / ALREADY_APPLIED / SUPERSEDED / REJECTED` 等明确处置，不能把已跳过版本统计为“实际写入该版本”。

### 14.4 Kafka、CDC和容量边界

数据库Publication显式限定 `publication.outbox`；禁止全库发布及连接器自动扩大捕获表。Debezium PG单Connector通常只有单Task，增加 `tasks.max` 不会直接并行读取同一条变更流。[O10][O11]

Kafka分区、Consumer分配、业务库并发、单分区热点均限制有效并行。扩Consumer前核对客户端／消费协议、分区数及业务库余量；不能只看总Lag。[O12]

Broker副本、ISR、生产者ACK、有限retention、毒消息处理、重放权限、consumer offset和幂等保留窗口都需要验收。Outbox/slot/Kafka/输入快照有各自保留责任；不能把日志保留称为“无限故障隔离”。

Outbox清理必须与可靠捕获及恢复策略一致。按时间分区时审计全局唯一性、父子Publication路由及锁；本版不规定“禁止所有DELETE”或“DROP零秒完成”。

**24.8分发存储约束：**只保留最小可消费payload或受保护不可变引用；不把“最小”误解为无法重现的裸ID。源载荷、Outbox、Kafka、输入引用、Inbox的期限和防重窗口联合校验，见16.8～16.11；不新增并行分发通道。

## 15. ClickHouse、读模型与分析投递

ClickHouse保留为历史分析层，PG保留当前事实、授权、回执和仍需恢复的关键状态。Console读模型不是第二套授权源。

分析链沿用：业务事实与最小分析义务同事务 → 有界批投递 → ClickHouse → 独立确认。Publication和Analytics不能共用完成游标、删除条件或故障预算。不为所有普通日志写关键Outbox。

分析事件有稳定ID、源版本、源发生时间、记录时间和payload_hash；重放保持身份。精确汇总需按事件去重或重建，不对可能重复输入直接累加后期待后台归并自动撤销重复。历史统计与当前列表使用各自watermark，延迟不伪装实时。ClickHouse插入去重有引擎与窗口条件，不能当成永久唯一约束。[O18]

Read Model故障可重建；历史重建必须有仍保留的源事件／归档，源已删除则明确不可还原，不能把“可重建”理解为凭空恢复任意历史。Projection更新有界，不能每个页面刷新扫描全部频道／视频。**24.8：当前投影只保留已批准页面/过滤需要的字段；历史投递使用字段白名单与获准时间粒度，不镜像所有PG表或复制整份频道JSON。**降采样不能删除尚未被Feature/恢复流程消费的源Observation，详见第16章。

新增分析写入器前看ClickHouse批次大小、合并/写入压力、磁盘、投递延迟；更多Writer不必然更快。分析与业务库慢时，在已规划保留窗口内只延迟对应分支；若共享CPU/磁盘争用或积压触及容量保护线，可以间接限制采集，此时必须显示具体原因。

## 16. 数据增长治理：少写、去重、有限保留与安全清理

**本章是24.8新增的实施约束，不代表生产代码已经实现。目标不是让数据永不增长，而是让增长来自真实新增实体、获准保留的历史和必要可靠性成本，而不是重复快照、重试、心跳或无界日志。**

当前实体持续增加，当前事实和必要索引仍会增长；固定容量不可能永久承载无限新数据。近期过程数据应随在途量和保留窗口变化，而不是随平台运行年限无界累积。必要主备、备份、不可变输入和小型读投影是有预算的冗余，不能为了“零冗余”破坏恢复、隔离或查询能力。

### 16.1 数据归属：一个权威源，副本各有用途和期限

| 数据类型 | 最小存储内容／归属 | 不允许的重复 | 保留方式 |
|---|---|---|---|
| 频道当前事实 | PG按稳定频道身份保存Current | 因不同Query、Worker、Full/Update重复建立完整频道记录 | 纳管期内按业务生命周期维护 |
| 视频／评论当前事实 | PG按平台稳定内容身份保存；子项引用频道／视频ID | 每次采样都追加完整内容副本；每条评论重复整份视频/频道资料 | 与正式采集范围和业务保留合同一致 |
| Query与来源 | QueryTerm、Binding、来源关系分别存 | 每次命中同词新建Binding；每条来源复制整个频道/视频正文 | 多来源归并；来源明细有限保留，超期按获准合同保留摘要 |
| 控制与恢复事实 | Plan/Request/Receipt/Inbox/Clock、冻结版本、小型计数 | 在每张任务表复制同一Raw/大输入/完整频道快照 | 活动及重放保护期间不可删；完成后压缩明细、保留必要防重证据 |
| 历史分析 | CH只接分析合同列出的观察字段、事件摘要、维度/版本 | 将PG所有表、完整Channel JSON及所有日志无差别复制到CH | 明细、汇总均有明确保留期限和空间预算 |
| Console读模型 | PG只保留列表/详情所需字段、状态摘要、水位、引用 | 每个页面一张完整频道副本；把Trace做成第二套业务事件全集 | Current按对象更新；历史视图引用受控历史源 |
| 代理/服务器/Worker观测 | 当前状态＋必要窗口汇总＋关键状态变化 | 每次心跳永久追加所有IP完整快照 | 当前记录覆盖；短期排障样本与历史汇总分别过期 |
| Publication | 有界业务payload或不可变输入引用＋event identity | 相同身份重试产生新发布事件；消息嵌入整频道全部历史 | Outbox、Kafka、计算输入、Business Inbox各有保留责任 |
| Raw／诊断样本 | 对象存储保存一次选定对象，其他位置保存引用/Hash | 同一响应在Journal、PG、Trace、Kafka、CH、S3长期各存全文 | 普通成功Raw默认不额外长期保留；恢复/争议证据显式保护 |
| 日志／错误 | 聚合计数、归一指纹、有限样本、关联ID | 每次重试都永久保存相同大堆栈/响应体 | 诊断数据按时间、字节、样本数共同限额 |
| 备份／副本 | 原有HA/备份方案、声明故障域和恢复窗口 | 无负责人、无限代数的快照或同故障域伪备份 | 按备份链和恢复目标安全轮转，不当普通缓存删 |

“权威唯一”是逻辑规则，不是要求全系统物理上只有一份数据。消费端业务投影、HA副本及可靠传输阶段的暂时多副本可以存在，但要列明目的、保留条件、预算和负责方。

### 16.2 当前事实：按稳定ID更新，不按采集次数复制

本章中的表名、字段名是设计示意，落地映射实际Schema，不要求新建同义表。

```text
同一个 video_id 被合法采集100次：
  Current仍是一份当前事实
  有必要的时效/观察/质量元数据
  有界的业务过程记录
  获准保留的历史指标点

不是：
  100份完整视频JSON + 100份完整频道JSON
```

频道、视频、评论及关系使用稳定业务身份和数据库约束去重；handle、展示名、临时URL、Worker实例ID不能代替稳定内容身份。相同实体被不同Query找到，只追加合法来源关系，不复制实体。一个Query在不同Country/Business Category下的Binding是不同业务对象，不是应去掉的冗余。

写入先按字段证据与版本规则形成合法变更，只更新确实变化的字段；已有字段未知/缺失不能覆盖成零或空。值从estimated变成exact、访问条件变化、来源质量升级同样可能是业务变化，不能仅比较数值或整个JSON字符串。

对于大型字段，重复提交不重写相同正文；Hash可用于一致性/快速比较，但不能跳过身份、执行权和字段质量校验。防重依靠受控事务与唯一身份，不能仅凭进程缓存或Bloom Filter判定“已有”而丢弃新实体。

### 16.3 “内容没变化”不等于“这次观察不存在”

区分实体的内容变化、一次新的合法观察、同一观察的传输重试：

| 场景 | 要做什么 | 不做什么 |
|---|---|---|
| 同一Submission原字节重传 | 返回原Receipt；必要重试统计受控累计 | 重复Apply、重复内容版本、再次记成功 |
| 新一轮采集成功，值没变 | 按原合同持久观察时间、质量/覆盖证据、必要Observation与Clock处理 | 复制整份内容快照；跳过必要的Feature输入 |
| 新一轮字段确有变化 | 合法更新Current，生成合同要求的历史/分发数据 | 无界保留每次采集的整频道历史 |
| 200但字段/扫描不完整 | 保存partial/错误及恢复义务 | 为节省存储而当作NO_CHANGE或完成 |
| 只收到心跳或收到过期结果 | 按身份和时间检查观测有效性 | 将last_seen伪装成成功采集时间 |

**不改变附录中的First-Seen/Recent算法、Observation、Ledger和Feature序号语义。**优化发生在字段去重、投递副本和已不参与恢复的历史保留层；不能先把原始业务观察聚合掉，再要求Feature凭摘要恢复原算法。

### 16.4 历史：保存有用的字段与时间粒度，不复制所有Current

历史合同至少声明：实体范围、字段白名单、生成条件、事件时间、时间粒度、质量标志、晚到/更正窗口、原始明细期限、汇总期限、查询能表达的精度。它与Current完整性合同分开。

默认不追加整份Channel/Video JSON作为每次历史。指标历史可保存必要的播放/点赞/订阅等数值、时间、来源质量和版本；静态长文本仅在合同要求且发生变化时保留版本。若业务只需每日趋势，可批准日粒度指标点；若需要每次观察、小时趋势或任意期间审计，就不能在未批准前降成每日一条。

历史生成可选“每个必需观察”“实际变化”“固定时间桶＋重要变化”等方式，但每个数据集只能按自己的获准策略执行；这不是新的一套采集/Clock算法。按变化保存会形成不规则时间序列，UI/分析必须展示采样口径，不能伪造均匀采样、精确日值或完整覆盖。

降采样不是简单取平均：播放量等累计计数的日点可按已定义事件时间取有效末值，吞吐计数按去重事件汇总；P95不能由多个P95直接求平均。具体字段规则在数据合同里固定。必须先完成去重、晚到/更正处理和聚合核对，再删除其唯一原始输入。

```text
近期：按获准精度保存必要明细
  ↓ 已过更正/恢复窗口，汇总核对完成
中长期：按业务实际需要保留小时/日/月摘要或精选明细
  ↓ 到获准保留终点
删除；只有声明了用途和预算的数据才归档
```

**冷归档不等于永远保存。**精确历史删除后，系统只能提供保留的汇总或明确的归档范围，不承诺还原任意一天的所有底层请求。原始明细和汇总的具体天数本次未替用户拍定，生产启用前必须批准；字段减少、时间粒度降低不能静默破坏现有查询承诺。

### 16.5 全链路：保留因果与证据，拒绝重复大载荷

完整业务链路来自稳定ID、阶段转换、输入/输出版本、可信Receipt和关联边，不要求每个阶段复制完整输入与响应。

- Plan/Request/Submission各保存其必要权威事实；Trace引用这些对象并投影状态，不新增另一套独立完成真相。
- 只因有新事实/状态转换才追加业务事件；页面刷新、定时轮询和重复心跳不能重复追加同一状态。
- 当前频道/计划摘要保留到最近成功/失败、当前等待原因、关联对象和版本；最近过程明细有期限，历史按合同转入CH或归档。
- 技术HTTP日志、堆栈、SQL样本可采样；必要业务结果、幂等回执、安全审计、失败预算不因采样丢失。
- 相同错误保留指纹、版本、首次/最近、次数和有限代表样本。需要精确影响频道数时，在限定窗口使用去重明细或有声明的近似算法；不能无界塞入受影响ID数组，亦不能把近似数量标成精确。

Raw按 `evidence_ref + hash + size + retention_class` 引用；凭据和敏感参数不进入样本。样本配额应覆盖错误指纹/版本和总字节，防止错误类型爆炸绕过“每类少量”的上限。故障调试临时提高采样必须有结束时间、空间上限和审计。

### 16.6 服务器与IP：不能把每次心跳做成永久历史

当前server/worker/proxy观测按对应身份更新；每批报告用 `node_boot_id + report_sequence` 防重，序号陈旧或重复不再次累加请求量。同一IP状态无变化，不追加第二份完整状态对象。

累计计数需识别重启/归零，不能把每次上报的累计值都SUM一次。趋势只写获准时间窗口汇总；assignment_generation、启停、人工迁移、健康状态转移等必要事件保留独立审计/诊断历史。低频全量快照用于对账和修复Current，不默认成为永久快照仓库。

Proxy Manager的本地缓存/日志、退出Worker记录、过期Pod标识和中心报告接收记录均登记期限。移除历史实例时保留仍需排障/恢复的身份映射，不能留下无法解释的Trace引用。保持“中心低频管理、本地实时执行”，不增加逐HTTP请求中心写库。

### 16.7 API、Agent、批次输入：一次事实，多处引用

一个Batch只保存一份不可变成员清单，各Request保存必要身份和指向清单/结果的引用，不在每个请求里复制整个30项响应。外部返回项独立验收、按请求应用，不能因避免副本就删除分项回执。

重试优先复用同请求已确认结果；模型输出/提示词/特征输入不在Plan、Request、Trace和日志里重复全文保存。允许复用结果的条件仍是原请求、输入版本/Hash、模型/策略版本与业务时效合同；不能跨输入或跨合法周期随意使用缓存。

冻结目标集必须持久、有界且在恢复窗口内可读，不能为省空间改成仅内存缓存，也不能引用随时变化的Current。多个义务确实共享同一不可变输入时可复用已有引用；首期不另造全局内容寻址/去重服务。

### 16.8 发布链：最小可消费数据，不靠“只传ID”伪节省

沿用第14章：事件包含业务需要的有界payload，或可稳定读取的不可变输入引用。不要为了少写几十KB，只发送ID后在Consumer重放时读到新版本，再当作旧版本结果；也不让Kafka事件/CH历史无限复制频道全部视频与评论。

Outbox本身能作为保留期内的不可变发布载荷时，不再无必要复制另一张同内容大payload表；已有受保护输入可以引用，但保留责任必须覆盖Consumer停机、追赶、重算与允许重放的完整路径。小载荷内联通常比一律制造大量小对象更简单，选择按大小/保留合同确定。

网络/CDC重放不生成新的业务event_id。只有明确“完整最新态替换”语义才能合并中间版本；Patch、删除/撤销、计费或要求逐事件的流程不能按channel_id压成一条。本次不启用全局latest-only，更不通过Kafka压缩策略擅自改变事件含义。

Outbox清理按第14.4的可靠捕获与恢复条件验证，不能只看created_at，也不能把业务DELIVERED和CDC进度合并成一个标记。捕获确认后可按合同清理源传输副本，而非要求所有副本永久等下游；相反，没有可核验捕获/重放依据时必须停止清理并告警。

### 16.9 每类数据必须有保留合同，不能只写“以后定期清理”

合同放版本库配置/Schema文档，复用已有发布检查和后台维护能力，**不新增“数据治理微服务”或新消息系统**。

| 合同项 | 必须说明 |
|---|---|
| owner/purpose | 谁负责、哪个业务读/恢复/审计场景需要它 |
| identity/write_mode | 稳定键，Current更新、不可变事件、汇总还是临时数据 |
| field_allowlist | 必需字段、敏感字段处理、禁止携带的大载荷 |
| retention_clock | 以源事件、终态、失去最后引用或其他何种时间起算 |
| online/detail/rollup/archive期限 | 每层具体保留多久；不默认归档无限期 |
| dedup/replay_contract | 重放入口、最大允许年龄、旧版本拒绝与防重证据 |
| cleanup_gate | 活动依赖、捕获/投递、引用、审计hold和恢复条件 |
| max_bytes/soft_limit | 总字节及必要样本/行数上限、预测保护线 |
| cleanup_owner/job/last_success | 由谁清、上次结果、重试预算和延迟告警 |
| query_degradation | 明细过期后UI能看什么；不得假装可查全量历史 |

业务Current通常是“纳管期间有效”，不能无理由强加日志式TTL。过程/历史/诊断原则上必须给有限期限；业务批准的长期审计例外有明确责任与独立预算。必要期限未填写时，生产配置审查失败，不解释成永久保留，也不能解释成立即删除。

### 16.10 安全清理顺序：先证明可删，再删除

```text
识别生命周期已满足的候选（有界批次，默认dry-run）
  ↓
复核：活动依赖结束、必要回执/捕获存在、恢复/重放仍安全、无保留hold
  ↓
需要归档时：不可变Manifest＋Hash＋可定位索引＋读取抽验
  ↓
小批释放大payload/过程明细，保留合同要求的小型幂等证据/摘要
  ↓
删除资格再复核；清理结果/失败可审计；核对实际空间回收
```

不可只用 `pending_count=0`、`age > 30d` 或“已经复制到CH”判定可删。仍可重试的任务、API/Agent依赖、未解决COMMIT_UNKNOWN、源输入引用和幂等窗口都要考虑。引用创建与GC必须有受控版本/状态检查，防止GC选中后又被新任务引用的对象遭删除。

Receipt/Inbox不能套用普通日志TTL。若要删除旧逐事件防重记录，必须证明所有可能再次到达的入口都已被约束：网络重试、Kafka、归档回放、人工操作、备份恢复后的旧队列；可以使用经过证明的连续序号高水位/关闭代次拒绝策略，但有空洞时不能只取max(sequence)。超出支持范围的旧事件明确拒绝或走受控重建，不允许作为新事件再次产生业务效果。

未完成义务过久：告警、限制新任务、恢复或由授权操作按原业务规则终止，不允许为满足空间上限静默删除。可丢弃诊断样本先减采样；已确认业务数据不作为腾空间的牺牲品。

### 16.11 清理实现优先用现有工具，仍要验证实际效果

| 存储 | 用现成能力做什么 | 必须验证的边界 |
|---|---|---|
| PG | 唯一约束、受控UPSERT、表级回收、适用的时间分区/批删 | UPDATE/DELETE旧行版本需VACUUM；普通VACUUM主要回收复用空间，不等于文件立即缩小；不可把VACUUM FULL当日常无锁清理。[DG01] |
| ClickHouse | 合理批写、TTL、分区、获准rollup | TTL删除/聚合在后台合并发生，不是精确到秒的硬上限；预留合并空间并监测积压。TTL不替业务去重/更正验收。[DG02] |
| Kafka | 按Topic配置有限retention时间/大小及合适segment | delete策略按时间或空间条件清理，大小预算按分区计算；慢消费者可能赶不上，不能只配置TTL而不监控最老未消费年龄。[DG03] |
| S3/兼容对象服务 | 生命周期/版本过期/multipart清理 | AWS能力有明确配置，兼容实现需另验；未引用的诊断对象和被恢复/重放保护的对象分前缀/类别，不对整个桶统一按天删。[DG04][DG05] |
| Temporal | Namespace关闭Workflow的保留期与官方清理能力 | 保留期针对关闭执行，不能靠它清掉仍活动Workflow；不直接删除Temporal数据库内部表；业务回执保留独立管理。[DG06] |
| Prometheus/日志/Trace后端 | 原生时间/空间保留与采样 | 调试日志、标签基数、实例 churn同样有预算；告警和样本丢失需明示 |

对象开启版本化后，只清Current对象可能仍保留大量非当前版本；multipart残留、删除标记也应纳入策略。[DG05] 生命周期变更先针对小范围验证，并审查对既有对象的影响，不能发布一次TTL配置就当作数据已安全清干净。[DG04]

### 16.12 容量计算：把必要增长与可控开销分开

按存储域分别记录逻辑字节和物理空间，避免把不同单位混成一个“冗余率”或重复计算副本。

```text
计划总空间 = 当前实体/关系/必要索引
           + 各有限窗口历史、过程和诊断数据
           + 在途/未交付/受保护输入
           + 批准的副本与备份
           + WAL、合并/回收/重建临时空间和安全余量

稳定输入条件下，某窗口数据占用 ≈ 该类有效生成字节率 × 保留时长
突发积压额外占用 ≈ ∫ max(产生率 - 安全处理/清理率, 0) dt
到保护线剩余时间 ≈ 当前安全余量 / 持续净增长率（仅净增长率>0时）
```

这些是规划估算，不是容量承诺。Current新增实体还在增长时，总空间继续增长是正常的；同一固定实体集反复刷新却不断产生完整副本是不正常的。数据已删除但PG/CH物理空间尚待回收，与业务实际新增要分开诊断。[DG01][DG02]

容量视图至少展示：按数据集的有效实体/事件数、payload/索引/副本/备份/临时开销、24小时/7天新增与净增长、过期未清理字节及最老年龄、重复提交数与新增持久字节、Raw样本量、IP心跳历史量、Outbox/slot/Kafka滞留、估计到保护线时间。不能只显示磁盘百分比。

不通过不断加磁盘掩盖清理失效；也不为了零增长删仍需保留的新频道、新视频或精确历史。预算将到线时先阻止可避免的新数据产生、降低非关键采样/新任务准入，再处理清理积压或扩容；有限介质无法同时支持无限输入、无限保留和永久不停机。

### 16.13 上线门槛与最低成本验证

每个新增表、索引、Topic、Bucket前缀、投影都必须回答：为何需要、唯一身份、谁读、写入频率、字段大小、预计增长、保留期限、删除资格和维护者。评审发现完整载荷在多处无目的复制时，先删除复制而不是新增压缩/分布式去重平台。

必测三组负载：固定实体集重复刷新；持续新增实体；下游停机后恢复追赶。分别证明：Current不随刷新次数复制增长、历史/诊断按合同有界、真实新增可核对、恢复证据未被误删、清理吞吐能跟上有效过期量。完整验收新增DATA-01～DATA-24，见第27章。

### 16.14 高可用不是可以删除的冗余

同步复制可用于约定故障域内的RPO目标，但需冻结提交级别、同步节点资格、切主fencing与确认状态；异步复制不能承诺零RPO。[O13]

PG Standby是同一逻辑库的副本，不是额外写主能力。Kafka、Temporal persistence、Control API、PgBouncer入口、对象存储和ClickHouse分别设计故障域；可重建历史分析允许的停机窗口不同于在线事实库。

一台服务器运行所有组件可用于开发／验证，不能称生产HA。少量服务器共置必须计入N-1后剩余资源、复制流量、磁盘故障域和备份离机；未经测试不承诺三台固定规格承载千万／亿级工作负载。

备份保留周期必须覆盖约定恢复点与链式依赖，冷归档不替代备份。恢复到旧备份后要复核Outbox、Inbox、业务版本和仍可回放事件的关系；保留策略缩短需要经过恢复演练，而不是仅证明平时查不到旧记录。

## 17. 安全职责：配置成熟组件，不自研协议

### 17.1 基础设施与业务边界

| 安全需求 | 负责层／成熟能力 | 业务仍需做什么 |
|---|---|---|
| 节点间传输加密 | 支持的CNI加密或现有私网VPN；标准TLS | 验证覆盖的真实路径，不自行加密包 |
| Pod间访问限制 | 支持策略的CNI＋NetworkPolicy | 维护少量明确的服务访问矩阵 |
| 外部入口HTTPS／服务TLS | Gateway／标准服务端与客户端TLS库 | 正确校验对端、主机名、过期与信任链 |
| 证书签发轮换 | cert-manager或已有PKI工具[O17] | 配置Issuer、权限和轮换测试，不写CA |
| 用户身份 | OIDC/既有身份服务＋成熟验证中间件 | 角色映射和对象级业务授权 |
| K8s管理权限 | Kubernetes RBAC | 最小ServiceAccount，不给Web通用cluster-admin |
| PG/Kafka/对象权限 | 产品原生认证、角色、ACL | 专用账号、限定库/Topic/前缀 |
| 密钥 | Secret Manager／K8s Secret及加密与最小权限 | 不泄露到日志、Query参数、Trace和心跳 |
| 业务命令 | Control API＋权威Store | Plan归属、当前epoch、是否取消、expected_version与审计 |

NetworkPolicy不是用户身份认证，也不是为每个HTTP对象授权；是否生效取决于网络实现。Cilium WireGuard等透明加密的覆盖有边界，同节点、hostNetwork、集群外／非Pod服务需分别检查，不能把“启用WireGuard”当成所有连接已经应用层mTLS。[O14][O15]

不要求全平台Service Mesh。优先选择一套满足真实路径的网络/身份配置，服务采用标准库接入。保留安全功能，但不叠加多套等价加密／身份系统。

### 17.2 最小访问矩阵

Collector可访问Temporal执行接口、授权输入接口、Ingest、节点本地代理；不能直连Crawler PG管理接口。Proxy Manager只访问Proxy Control和其授权代理供应商。Ingest/Feature/Planner/分析投递各有最小DB角色。Business Consumer写业务库、通过受控路径获得固定版本输入和回传回执。

SSRF防护：采集目标、可访问域、重定向、元数据地址和内网地址按业务合同校验；不得让用户输入任意URL变成服务器内网访问器。审计保留操作者、资源、期望版本、结果、原因和命令ID；Hash只证明一致性，不代替身份认证或防篡改存储。

## 18. 可观测性、错误中心与业务读模型

### 18.1 三层下钻

```text
业务层：为什么没采／没更新／不完整／没交付
  ↓
执行层：Plan、Domain、Request、Batch、Submission、Receipt、Server/Worker/Proxy
  ↓
诊断层：结构化日志、技术Trace、Temporal历史、PG/网络/容器指标
```

业务关键状态从权威事务／可靠事件派生，不能从采样日志猜完成。技术Trace可以采样，丢样时标记证据缺口；“所有问题都能定位”不是无条件承诺。保留SDK/build/policy版本，才有可能把回归定位到版本。

### 18.2 错误与Bug线索

首页展示经聚合的线索：错误类别、首次/最近出现、次数、影响对象数、构建版本、阶段、最近有效回执、当前自动动作、负责方、日志/Trace/Plan链接。固定指纹可由规范码＋阶段＋归一堆栈＋版本组合，避免每个channel_id生成一条独立告警。

区分 `代码缺陷候选 / 上游限制 / 配额 / 配置 / 容量等待 / 目标合法条件 / 未分类`。429、代理等待、私有视频、冷却状态不能自动升级为“严重Bug”。同频道连续失败也需看证据。错误聚合服务失效不能阻塞事实提交，关键错误和审计仍按所需耐久等级保留。

业务Trace表示因果图，不能强行按时间排成 `Full→Update→Agent→API`；多来源、并行、重试、后继计划使用关联边，单个trace_id不代替业务身份。

### 18.3 避免观测成为新瓶颈

Prometheus保留可控基数的角色／阶段／结果／原因族。channel_id、request_id、proxy_id及原始URL放明细或Trace，不作为全量时序标签。节点标签也需控制保留规模。

不要为每个HTTP调用同步写PG。关键阶段事件随既有事务／可靠义务产生，技术明细批量、采样或异步送诊断后端。观测管线过载有自己的丢弃/采样规则；不能丢业务回执来保日志。**24.8：错误指纹/版本的代表样本、样本总字节、堆栈/Raw期限必须受控；计数与诊断样本分开，不因采样把真实失败次数改小。**业务Trace和引用过期后的可见性按16.5明确展示。


查询使用已维护汇总和有界系统统计，不每次页面刷新全表COUNT或扫全Bucket。对于无法精确取得的容量、去重实体数、预测值，显示估算/水位/采样口径。跨库表示与物理副本分别列，避免把合理备份误报成重复业务数据。

历史详情超过保留期显示“明细已过期，可查看日汇总/归档（若有）”，不能返回空表并暗示当时没有事件。清理失败是维护告警，清理动作仍需权限、dry-run和安全条件，不能给业务用户一个绕过保护的“全部清空”按钮。

## 20. 吞吐量的正式定义：先把统计对象对齐

### 20.1 五类速率必须同时保留

| 名称 | 单位／唯一身份 | 表示什么 | 不能代表什么 |
|---|---|---|---|
| 请求吞吐 Request Throughput | 外部HTTP调用/秒，含attempt | 网络调用工作量与成本 | 完整频道产出 |
| 捕获吞吐 Capture Throughput | 校验后结果单元/秒、字节/秒 | Worker取得了多少可提交数据 | 已中央持久化 |
| 持久应用吞吐 Apply Throughput | 首次应用的logical_batch_key/秒；行/字节另列 | 真正发生了多少去重业务应用 | 整轮Plan已经完整成功 |
| 成功计划吞吐 Successful Plan Throughput | 按业务合同成功的plan_id/秒，Full/Refresh分开 | 本轮所需域已达到成功口径 | 业务库已交付、每天去重频道数 |
| 交付吞吐 Delivery Throughput | 每destination首次接受的event_id/秒 | 下游事务已接受 | 源采集速率或长期无限缓冲能力 |

另列“单位时间成功更新的去重channel数”与“首次达到完整的频道数”。同频道一天两次合法计划，可产生两次成功Plan，但当日去重频道只计一次。有效检查没有变化属于成功观察，不应要求每次都新增视频。

`Plan Settled` 包含允许的partial／terminal等结果，不能直接作为成功计划计数；统计必须使用明确的success/coverage政策版本。用户关心“采集速度”时，默认同时展示**Apply吞吐＋成功计划吞吐＋完成延迟**，而不是只显示HTTP QPS。

### 20.2 计数规则

每个成功业务转移只能产生一次逻辑计数。HTTP重试、RPC重传、ACK丢失、Consumer重放都不能重复增加成功产出。高频诊断Counter可以按attempt计数，但标签和名称必须说明它不是去重业务计数。

精确报表来自业务事件的幂等投影或可核对事实，具有watermark；Prometheus用于近实时诊断，不被当成金融账本式精确唯一计数库。自动容量策略读取局部实时资源信号，不能完全依赖可能延迟的ClickHouse业务统计。

### 20.3 禁止跨单位直接比较

```text
QueryRun/s ≠ 候选频道/s ≠ Channel Plan/s ≠ HTTP/s ≠ Submission/s ≠ SQL事务/s ≠ Event/s
```

一个Query可能发现多个频道，一个Plan可能产生多个Submission，一个Submission可以包含多条视频事实。禁止把这些数字沿箭头相减、计算百分比后认定“中间丢了多少”。存量、流量、总attempt和去重产出必须标注。

### 20.4 同单位积压守恒

对同一队列、同一类唯一对象、同一统计窗口：

```text
期末待处理 = 期初待处理 + 新进入 - 已处理离开 - 已确认终止移出
```

例如“已耐久接收、尚未应用”的Submission队列，必须明确已拒绝、隔离、被替代和Fast Apply分别怎么计入；Fast Apply可直接进入已应用，不必虚构一个等待状态。队列数量、总字节、最老年龄都要记录。

**示例，仅作定位演示：**同一批结果类，持续耐久接收1000个唯一Submission/分钟，应用600个/分钟，明确终止移出50个/分钟，则该队列增长约350个/分钟。结论是“接收到应用区间存在持续积压”，还不能断言数据库硬件不足：可能在等前置回执、校验、Apply额度、连接、锁或SQL。

## 21. 性能模型：并发槽、工作负载与扩容收益

### 21.1 先定义工作负载profile

至少分Discover搜索、Full、Update-About、Update-Video、Agent-only、组合Refresh及恢复流量。记录国家／客户端／版本、输入大小、目标数量、评论要求、API/Agent比例、失败重试比例、冷热数据、代理质量和外部时效。

模型中的数字从代表性数据获得，不假定“一个频道更新=一次HTTP=一个Pod”，也不把所有采集器都假定为95%时间纯I/O等待。解析、校验、压缩、Hash、GC、事件循环和本地模型都可能耗CPU。

### 21.2 同量纲容量模型

对工作类j，其到达率为 `λ_j`；每个业务单元对资源r的平均需求为 `a_rj`。在定义过的测量区间内，规划需满足：

```text
Σ_j (λ_j × a_rj) ≤ 资源r的安全服务预算C_r
```

例：若 `a_rj` 是字节/计划，`C_r` 就是字节/秒；若是CPU秒/计划，预算是可用CPU秒/秒。并发上限、每日外部配额和磁盘保留还需要独立约束，不能全部塞入一个不同单位的min函数。

固定业务混合比例后，才可以把各资源换算为同口径的“等效业务单元/秒”做最小容量估算；外部抖动和尾部重试会改变需求，应留实测余量。

### 21.3 Little's Law只用于已定义、近稳态的队列

```text
平均在途数 L ≈ 平均完成率 λ × 平均逗留时间 W
```

必须说明是HTTP、Submission还是Plan，W包含哪些等待。在持续积压、极端长尾或工作量变化时，不能用两秒单次请求耗时估算整个频道计划的并发需要，更不能把并发连接数当进程或Pod数量。

### 21.4 同步关键路径与异步支路

采集Apply主要受输入供给、Worker/Proxy/外部请求、通信、Ingest和PG路径约束。成功计划还取决于**该计划实际必需**的API、Agent和Feature回执；Agent-only与Video-only不能同套分母。

Kafka、Business DB、ClickHouse不是正常Apply的同步等待节点。在独立资源和有限保留预算内，慢下游只增加对应lag；共享CPU/磁盘、可靠义务积压或存储水位接近上限时，会间接触发源端保护。**异步不等于永远不影响采集。**

长期生产率持续大于下游处理率，任何有限Kafka或Outbox都会最终耗尽。必须扩真正瓶颈、降低新增速率或批准改变保留/产出策略，不能只用“后面慢慢追”解释永久不平衡。

### 21.5 扩容效率

```text
Scale Efficiency = (同口径新有效吞吐 / 原有效吞吐) / (新有效资源 / 原有效资源)
```

资源相同的节点／Worker可用数量；混合硬件用实际CPU、内存和可用槽等画像分层比较，不能把一个4核Pod与16核Pod等价。

示例：20个同规格Worker得到10000成功Plan/小时，40个得到19000，则该次对照效率95%；80个得到23000，相对40个约60.5%。这些仅是算式示例，不是本项目实测，也不能独自定位瓶颈。

相同版本、业务混合、代理额度、数据集、请求成功率、热身和测试时长才可比较。Ready实例、实际执行槽、代理绑定是否增加要同时记录。有限任务集跑完／调度主动限额／约定成本上限导致不增长，可以是正常结果，不一定是架构故障。

对Histogram必须先正确合并bucket再计算分位数，不能平均各Pod的P95。窗口、采样、延迟、计数器重置必须显式处理。观测采样缺失时显示“信息不足”，而不是零延迟或100%成功率。

## 23. 加Worker不涨吞吐：定位流程与证据表

### 23.1 排查顺序

```text
0. 指标对象、成功条件和测试工作量是否一致？
1. 是否存在足够可执行任务？是否被策略/预算主动限制？
2. 新Worker是否Ready、匹配版本/Task Queue且真的拿到活？
3. 本地是否等待代理？绑定IP/出口/会话额度是否真的增加？
4. 外部请求成功率/耗时/重试是否变差？
5. 宿主机、事件循环、解析、Journal和网络是否饱和？
6. 结果是否在发送/接收/解码/校验排队？新Ingest是否实际接流？
7. Apply额度、连接、锁、SQL、提交、复制哪个区间等待？
8. Apply正常但计划不完成：查API/Agent/Feature/封口/回执。
9. 只有交付/分析不增长：分别查CDC/Kafka/Business和分析投递/CH。
```

### 23.2 候选瓶颈与应对

| 候选 | 支持证据 | 要排除的混淆 | 优先动作 |
|---|---|---|---|
| 无合格需求 | due/admitted/eligible很少，Worker空闲 | dashboard落后、所有工作被错误过滤 | 检查Clock/准入，不买机器解决 |
| 派发或Worker配置 | 队列等待升高，新Worker无任务，槽/版本/路由不匹配 | 外部依赖占满执行槽；网络到Temporal失败 | 修复poller/队列/版本，按SDK调参 |
| 本地代理容量 | acquire_wait增、健康路由在额度上限 | 多端点其实同出口、错误配额、心跳陈旧 | 合法增加资源或调整分组；不是盲目加HTTP并发 |
| 外部限流／访问条件 | attempt增而有效结果不增，RT/429/挑战增 | Proxy Manager网络故障、解析器回归 | 按来源分类、退避/冷却，不用无限重试 |
| Worker算力／共享主机 | 单核/事件循环/GC/解析/压缩饱和 | 仅平均CPU低、quota throttle | 优化热点或增加实际物理算力，控制混跑 |
| Journal／本地盘 | pending bytes/写延迟上升，磁盘到保护线 | 上游已停但恢复重放仍继续 | 排空和减少新任务，绝不删未确认结果 |
| 网络／发现／LB | 重传、带宽/MTU/DNS/TLS异常，实例负载不均 | ACK慢实际是SQL慢；监控聚合误导 | 分段计时、复用、修正路由/发现，测新实例接流 |
| Ingest CPU | decode/validate排队，实例繁忙，PG提交稳定 | 线程池限制、异常大包、内存限制 | 扩Ingest/优化批大小；总DB预算保持受控 |
| 连接池 | pool_wait升，PgBouncer排队 | 长事务、热点锁、后端多池失衡 | 先定位占连接原因，有证据才调池 |
| PG查询/锁/存储 | SQL/COMMIT/wait显著上升，Apply队列增长 | 应用限流过严、同频道重复任务、同步Standby慢 | 按SQL、锁、IO证据处理，必要时限流和升配 |
| API／Agent／Feature | Apply正常，必需域pending/最老年龄升 | 计划其实不需要该域、旧版回执错关联 | 按域补能力/配额/修复状态，不重采已应用域 |
| CDC／Kafka／Business | 仅发布延迟，slot/consumer/目标DB证据异常 | 错误消息阻塞、单分区热点、输入版本不可读 | 在有效并行度内扩，处理毒消息/版本/保留预算 |
| CH／历史投递 | history watermark落后，投递/合并/存储慢 | UI把陈旧统计当采集变慢 | 隔离查询与写入资源，补投递，保留源义务 |

“候选”是诊断结果，不是自动根因证明。至少要有时间相关、同量纲积压和具体服务时间/资源证据；必要时用隔离环境单变量试验确认。多个瓶颈可同时存在，不能强制每次只给一个红色百分比。

### 23.3 三个具体判断例子

**例A：加Ingest有用。**序列化/网络正常，Ingest解码队列增长且每个实例CPU受限，PG等待和提交延迟稳定；增加Ingest后确实分担新RPC并使唯一Apply速率上升。此时扩入口算力合理。

**例B：加Ingest没用。**新实例都能接流，但多数时间等待同一热点频道锁；更多并发增加阻塞。先消除重复冲突工作／缩短事务，不把逻辑串行点误当算力不足。

**例C：采集正常，业务交付不涨。**Apply与成功Plan稳定，Kafka lag持续增长且Business提交变慢。问题在交付支路；不能先扩Collector。只要保留余量安全，采集无需立即停；持续失衡则触发该支路的上游保护策略。

## 24. 扩缩容与Capacity Guard：两个控制回路

### 24.1 扩副本与发工作分离

```text
KEDA/HPA：依据需求与资源增加/减少处理器
Admission/本地Limiter：控制现在允许启动/提交多少工作
```

副本数不代表允许无限并发。HPA多指标按各指标副本建议取较大值，不能把“PG高压”作为另一个普通扩容指标就期待自动抑制队列触发的扩容；KEDA的cooldownPeriod也不等同于所有非零副本间的缩容稳定窗口。[O08][O09]

本版不建设新的通用Global Scheduler。Capacity Guard是已有Planner/控制API中的版本化策略模块，加上各服务本地限流器；借现有指标管线传递容量快照，不让每次HTTP都调用中心获取许可。

### 24.2 总额度与本地额度

Control下发有有效期的角色/节点额度，包含reserve与版本；各本地执行器在额度内独立运行。额度分发必须确保有效额度之和不超过总预算，过期快照不能被新旧实例重复使用。可先使用按最大并存副本计算的静态配额；动态额度需要通过失联／换代测试后启用。

Ingest/Feature等可用“扩实例但降低每实例写槽”的方式增加解码或非数据库算力，同时保持PG总事务上限。代理额度由本地Proxy Manager执行，中央只分配粗粒度资源，不恢复Rota式逐请求往返。

### 24.3 保护状态机（本版设计）

| 状态 | 进入条件 | 允许行为 |
|---|---|---|
| NORMAL | 需求、延迟、空间在验证区间 | 按预算工作；可受控扩容 |
| CONSTRAINED | 持续排队／关键延迟上升、扩容尚未到位 | 减少新增、优先完成在途；扩真正瓶颈 |
| PROTECT | 空间／恢复责任／依赖资源接近硬边界 | 停止受影响的新义务，保留回执、收尾与有限恢复 |
| RECOVERING | 压力下降且恢复窗口满足 | 分批增加额度，重试带抖动，不集中全速恢复 |
| METRICS_STALE | 容量信号超时或控制不可用 | 使用批准的保守额度；到期后禁止无依据扩张 |

阈值、持续时间、恢复滞回按资源/业务profile配置并审核。不能全平台只设CPU75%，也不能瞬时抖动就停全系统。CPU高但队列与延迟正常时不自动认定故障。

### 24.4 优先级与公平

优先保护已确认结果、回执查询、必要结算、最小恢复；一般先削减新增Discover和首次Full，但仍保留各业务类的最低公平份额，避免更新频道或小国家/分类长期饥饿。人为优先级和成本约束要有审计。

KEDA需要看到“有资格但未获准启动的需求”，否则所有工作被Admission挡在队列之外会导致队列长期为零而不扩容。分别输出合格需求与已准入队列，不能靠无界预发任务刺激扩容。

### 24.5 扩容时间差、缓冲和恢复

在新Pod真正Ready并能服务之前，不增加对应服务能力估值。缓冲覆盖扩容感知、调度、镜像拉取、初始化、连接热身及已接单输出；预算包括Journal、入口内存、中央已接收数据和存储，不只看队列条数。

Journal达到软线先减少新采集；硬线不接新的高成本工作、明确报告容量不足；已确认义务不能静默删除。纯网络流控不能让无界对象列表或日志无限堆内存。

<a id="chapter-25"></a>

## 25. 缩容、强杀与网络分区

正常缩容：主动停止poll/接新活 → 有界完成当前安全单元／封存Journal → 尽量提交并核对回执 → 停止本地代理使用并归还本地额度 → 退出。Readiness变化不能替业务停止poll；K8s宽限期后仍可能强杀。[O16]

Ingest不可达时无法“强制Flush成功”。因此必须同时实现非优雅路径：已中央确认的结果由中央恢复，未确认数据按持久检查点和保留Journal恢复；本机数据彻底丢失时，按原授权允许受控重采，而不是伪造完成。

节点失联不能立即认为它停止请求。Plan写入通过epoch/fencing拒绝旧执行；IP迁移通过第10章的本地到期和真实撤销保证范围内安全。取消不能证明外部请求未发生，也不能免除可能的重复计费。

应用最小收尾时间、终止宽限、外部调用总期限和本地会话时限须匹配。不能把固定60秒写成所有任务的成功保证。滚动、缩容、失联分别测试；备份恢复和应用重启不是同一测试。

## 26. 阶梯压测与定位实验

### 26.1 试验层次

1. **组件试验**：固定合法Submission测试Ingest解码、Apply、数据库；使用隔离命名空间和测试目标，不给生产Business重复送真实事件。
2. **链路试验**：完整运行Discover／Full／Update＋API/Agent依赖，验证计数与等待路径。
3. **弹性试验**：相同负载N→2N→4N，实际增加算力和已授权代理额度，记录下游余量。
4. **故障试验**：延迟、断网、slot/配额不足、节点丢失和恢复重放。

不在生产库上运行未审查写入压测；同ID重放只测幂等路径，不能用它代表真实首次写入吞吐。应使用等价的新业务身份和隔离数据集，记录测试数据清理与归档规则。

### 26.2 单变量定位

| 试验 | 保持不变 | 观察结果 |
|---|---|---|
| 固定响应回放 | 解析器、结构与大小分布 | 排除外部网络后是否仍慢 |
| 合法结果直达测试Ingest | payload分布、首次写入比例 | 通信/校验/Apply的处理能力 |
| 仅调整Ingest实例 | PG总连接/写并发不增加 | CPU型瓶颈是否缓解 |
| 有限调整PG并发 | SQL/批大小/硬件固定 | 找最佳并发点，防止过量竞争 |
| 分散热点与固定热点对比 | 总数据量和SQL相同 | 识别同频道串行/锁热点 |
| 固定代理额度只加Pod | 实际IP/出口/并发不变 | 证实外部许可上限不是算力上限 |
| 新实例流量分布 | 业务负载和LB模式固定 | 是否仍黏旧连接 |
| 暂停下游目的地 | 已设定保留预算 | 测短时隔离和长期保护，不无限等候 |

### 26.3 报告必须保留

硬件与拓扑、版本摘要、配置/Schema、工作负载profile、初始积压、Ready实例时间线、实际槽位、代理额度、请求/Apply/Plan/Delivery速率、分段分位数、错误与重试、队列条数/字节/年龄、空间/费用、收尾及清理结果。

#### 4.3 Full 的完成条件不要简化

`assertFetchCheckpoint`/`closeFetch` 关心的是冻结目标的 Detail 是否已走到规定状态、每条是否有 disposition、Hash/数量是否匹配。**这允许目标被排除或延迟处置，并不保证每个目标都变成完整的公开视频记录。**[F4](#src-f4)

```text
目标已走完当前采集路径
        != 该视频已经 stored
        != 该频道 Publication readiness 已通过
        != 业务库已经 DELIVERED
```

【风险】Full 的个别 `done`、候选 `deferred` 与界面的“完成”容易混读。目标文案应显示“已处理目标数、已入库、待后续确认、已排除”，而不是统一成功数。

#### 5.3 Recent Sampling 当前公式与配置

以下是 `incrementalVideoPlanner.js` 的算法摘要，不是本版发明的新策略。[I2](#src-i2)

| 项目 | 当前规则 |
|---|---|
| 配置校验 | Plan 的 `planner_config_version` 必须与配置版本匹配 |
| 近期窗口 | 默认 30 天，可配置；待补全目标可按资格规则突破普通日期筛选 |
| 陈旧阈值 | 默认 7 天；缺少 player 观测时间的处理沿既有规则 |
| 变化概率 | 已有合法 learned probability 优先；缺失时使用默认变化值与新鲜度组合 |
| Player Score | `0.6 × staleness + 0.4 × changeProbability` |
| 候选准入 | 待 Enrich、缺少 Player 观测、或达到默认 0.55 的刷新分数阈值等 |
| 排序 | 待 Enrich 优先，再按分数和稳定内容身份排序 |
| Player 数量 | 同时受候选数、建议额度、`floor(player_cap × factor)` 约束 |
| Next 子集 | 属于已经选中的 Player 集合；受 `next_cap` 与交互需求额度限制 |
| Next Score | `0.7 × nextStaleness + 0.3 × freshness` |
| 排他 | 已在 First-Seen 的视频不再进入 Recent；活跃 Enrich 租约要排除 |

**需单独评估而不默改：**采样新鲜度函数中有固定 30 天因素，而候选 recent window 可配置。扩大配置窗口不代表所有评分因素同步改变。先做现有行为回归，再决定是否调整算法。

#### 5.4 First-Seen 的中途提交不能在重构中丢掉

当前代码先处理 First-Seen 阶段，可保存内容与 `first_seen_ledger_status=pending`；到最终 Observation 时再消费 ledger。这样 Recent 中途失败，不必把已经获得的首次发现证据重新采一遍。[I1](#src-i1)

【目标】结果包与 Apply 按**有界逻辑批次**建模。允许先应用一批 First-Seen，再完成后续 Recent。每次已确认的内容写入，必须同时保存足以继续补齐 Observation/账本的恢复证据。不能把这个模型改成“所有视频结束后一个巨大事务”。

#### 5.5 latest-30 追赶策略的正确表达

`gap_abandoned_latest_30` 是已有明确策略，不是异常被吞掉。记录必须同时展示：

```text
coverage = policy_limited
原 stop_reason = catchup_limit
本轮采用最新 30 条
被放弃的锚点 / 原扫描身份仍保留
```

这里 `coverage` 是【目标】展示字段，旧协议继续保存原有 gap_abandonment。不得将旧 `complete:true` 无条件解释为“补齐此前所有历史”，也不得在重构中未经批准取消该政策。[I1](#src-i1)

#### 6.3 三类容易误判的内容

**播放／访问状态。** 显式 private、uploader_removed 与泛化 `video unavailable` 的证据强度不同；年龄、地区限制与频道不存在不同。`youtubePlayability.js` 有更细分的 content/inconclusive/collection_failure；上层不能丢失 reason_code 后只保留一个“不可用”。[Y3](#src-y3)

**内容类型。** Short/Live 类型必须保留 source 和 authoritative。Uploads 中的跳转或直播提示可参与候选判断，但不等价于可信 Player 类型结论；没有类型证据不能按短时长猜 Shorts。[Y4](#src-y4)

**空值。** `unobserved` 与已经观察到的空数组、空描述和零计数不同。字段质量标记是业务契约的一部分。现有合法的 disabled / zero_from_surface / estimated 规则保留；新系统只禁止“把未知随意填零”，不禁止明确政策产生的零值。[Y6](#src-y6)

#### 6.5 同一个 terminal，在不同对象上不是同一件事

| 名称 | 实际含义 |
|---|---|
| `terminal_excluded` | 本次候选不作为正常新视频落库；某些原因仍设置未来复查 |
| Enrich `terminal` | 该补全工作当前有访问条件结果；不代表整个频道失败 |
| checkpoint `settled_error` | 这条网络证据处理结束，可以推进阶段；后续业务可能 deferred |
| binding/Run `terminal` | 当前业务运行已结束或预算终止；是否另开恢复意图有独立规则 |
| Temporal 执行结束 | 工作流执行状态；不等于所有外部业务事实或交付回执都已完成 |

重构后的 Dashboard 要显示对象类型与原因，禁止只显示一个红色“terminal”。

#### 7.3 直播回放播放量估算必须单独标识

这是 `videoDetailApiFallback.js` 中的**既有启发式**：当已结束的公开直播回放在 YouTubeJS 和成功官方 API 中均缺少播放量，且官方点赞数等条件满足时，使用 `round(like_count / 0.025)`，输出 `view_count_status=estimated`，并保存方法、比例和原因。[A1](#src-a1)

不能把这个公式当作外部平台的真实统计规则；不能移植到普通视频、私有视频、进行中直播或 API 本身失败的情况。分析界面须区分 exact 与 estimated，不能拿估算值当精确真值校准其他策略。

#### 7.6 SessionContext：采集器内管理，不再造全局凭据平台【目标】

已有的 process／session／lease 边界继续保留。本轮给每次网络执行明确 `session_id`、客户端类型与版本、路由版本、适用端点、必要的凭据作用域／有效期和失效原因；敏感值只在受控凭据存储与运行内存，不进入结果包、Issue 或分析。

Rota 判网络资源权限，采集器判当前客户端会话是否满足其支持的访问契约。网络超时、会话失效、配额不足、访问限制和解析漂移分别记录；不能见 403 就回收一个健康 IP，也不保证增加 Token 就能解决所有挑战。

不建设“所有视频共用一个 Token”的池，不默认所有端点都需要同一 Token。所用 SDK 的凭据与客户端能力按固定版本测试；不足或受限时走现有授权、等待和有界终止规则，不通过绕过访问限制换取成功率。此节是目标契约，不声称已审计所有当前凭据缓存实现。

| 扫描不完整 | 保存目标和 scan 证据，Full 的有界目标口径独立 | 部分发现、Recent 跳过、不推进完整发现游标 |
| 中途保存 | Uploads 与逐候选 Detail 回执 | Item 检查点 + First-Seen ledger + 最终周期回执 |
| API 开关 | fetch contract 与配置共同决定 | 主入口环境开关／远端 frozen apiPolicy 决定 |
| API 未返回 ID | 保留访问未决，不冒充删除证据 | 同左，原项仍由其恢复／处置规则管理 |
| 内容已有类型 | 访问更新不随意丢已有类型 | 刷新及 Enrich 同样要保护已有证据 |
| 收口依据 | 固定目标全部处置 + fetch receipt + 后续交接 | Discovery/Recent/ledger/游标/生命周期/Batch finalized |
| 并发（本次读取入口） | serial Detail loop | serial checkpoint/whole-channel Detail loop |

**不得把这张表改写为一个没有 mode、stage 和 context 的“通用抓视频函数”。** 可以复用数据提取、校验和证据合并，流程上的业务差异应显式保留。[F2](#src-f2)[F4](#src-f4)[I1](#src-i1)[I3](#src-i3)[A1](#src-a1)[R2](#src-r2)

#### 8.3 已有阶段状态与目标统一状态的映射

```text
网络侧抓到并保存了一条详情          -> captured（现有）
采集错误已记录，可处理下一条        -> settled_error（现有）
候选决定存储/延迟/本次排除          -> disposition（现有）
中心拥有完整可恢复的该提交          -> RECEIVED（目标统一回执）
对应逻辑批次的源事实已原子应用      -> APPLIED（目标统一回执）
业务接收端持久接受对应发布版本      -> DELIVERED（目标统一回执）
```

这些不是一个表里的必然直线状态机。一次网络结果可能包含错误；一个 captured 结果仍可能被判 deferred；一次完整结果接收也可能因授权或 Hash 冲突而不能应用。保留对象和层次，禁止盲目一对一重命名。

### D.2 原ROTA码退出新运行时的版本化方案【本版新增设计】

原 `catalog_version=1.0.0` 继续支持历史读取。建议新协议使用 `1.1.0`：64个非ROTA码含义不改；以下5个旧规范名称停用于新发事件，由对应新名称与明确证据替换，总规范项仍为69。实现前固定Schema与黄金样例，历史存量不原地改写；不能只做字符串替换而丢失原native_code/cause。

| 原历史码 | 新规范码 | 新模块证据与范围 |
|---|---|---|
| ROTA.LEASE_LOST | PROXY.ASSIGNMENT_EXPIRED | 本地Assignment/会话授权已过安全有效期或被合法撤销；停止受影响的新网络操作 |
| ROTA.NO_READY_ROUTE | PROXY.NO_READY_ROUTE | 本机授权分组无符合端点/国家/并发要求的可用路由；是等待，不是频道无效 |
| ROTA.COMPLETION_UNKNOWN | PROXY.SESSION_CLOSE_UNKNOWN | 本地会话终止/资源释放状态尚未确认；仅本地恢复，不新建中央completeTask协议 |
| ROTA.BUDGET_EXHAUSTED | CTRL.RUN_BUDGET_EXHAUSTED | 核验原Plan/Run真实已用预算后形成；不是通过换IP、换Worker或新request重置预算 |
| ROTA.EXECUTION_BUDGET_EXHAUSTED | PROXY.ROUTE_BUDGET_EXHAUSTED | 本次执行换路预算已耗尽，不等于整个Business Run预算耗尽；结束当前执行，后续恢复先核对剩余业务总预算 |

旧码如没有相同新语义，不强映射：保留历史native字段与记录版本。通用 `AUTHZ.ROUTE_STALE` 继续表示路由代次不匹配，不能用数据库内容CAS冲突冒充。新增此映射是规范设计，不表示新协议已实现；所有接口必须通过兼容测试后才切换生产发码。

### D.3 旧验收适配

T/C/D/P/Q/BC中的数据正确性目标保留。直接提及旧Rota的场景在本地Proxy层注入授权撤销、节点失联、预算与会话收尾故障；“旧Finalize”场景在最后领域证明事务和提交后可靠通知边界注入故障。C系列Streaming场景用于启用流式路径的部署；普通有界RPC也必须通过等价的大小、断流、回执与扩容分流验收。不得以更换协议为由跳过核心幂等和耐久性测试。
