# M3：持续更新

起草：2026-10-08。目标：已完成首次采集的真实频道进入**纳管**，About、视频、Agent 三类数据各自到期、各自更新；每次只做到期的部分，失败只补未完成部分，旧结果不覆盖新结果。频道发现（Discover/Query）放在本阶段之后，见文末。

设计依据：[24.8 方案](../24.8_爬虫平台完整重构方案_数据增长与存储治理版.md)第 5.2、7、16.4 章；[开发计划](../业务平台开发计划_讨论稿_2026-09-23.md) 6.2 节；旧系统 `services/feature-engine` 策略 `v16-rule-7`（2026-08-10 起生效）。旧值只作初始建议，逐项标明出处，确认后才算定案。

## 起点

M2 已有：真实计划（`source_mode=youtube`）、ABOUT/VIDEO/AGENT 三个领域、目标冻结、分批回执、中断只补未完成批次、Agent 输入快照与 Hash 校验。

M3 需要补的：

- 频道没有纳管状态，也没有任何到期时间；计划只能人工创建。
- 只存当前事实（`m1.channels.about`、`m1.videos.data`），没有用于判断增长和发布规律的历史。
- 视频只有"首次采集最近 N 个"，没有"上次之后新发布了什么"和"近期视频数据刷新"。

## 顺序

| 步骤 | 内容 | 完成标准 |
| --- | --- | --- |
| 1 纳管与 Clock | 频道纳管状态（纳管/暂停/移除）；每个领域一份 Clock：`due_at`、`last_success_at`、`retry_at`、`policy_version`、决策原因；首次采集完成后按策略写入首个到期时间 | 契约与 Store 测试；控制台频道页显示三类到期时间和原因 |
| 2 调度器 | 周期扫描到期频道，每个频道生成**一个**冻结的更新计划，`required_domains` 为本次到期的领域（7 种组合）；同一频道同时只有一个活动计划；工作区级并发与每日预算上限 | 时间可注入的调度测试；重复扫描不重复建计划；预算满时排队而非丢弃 |
| 3 视频增量 | VIDEO 更新拆为"新视频发现"（上传列表扫到已知视频或上限为止）与"近期视频刷新"（重采播放/点赞/评论数）；删除、私有等变化记为不可用标记；复用 M2 的目标冻结与分批回执 | 录制响应的离线测试；真实频道新发布视频能被发现；只刷新约定范围 |
| 4 About 与指标历史 | About 更新；订阅数、播放数、视频数按天保留一条历史（不按采集次数复制），供增长判断使用；按 `source_revision` 保证旧结果不覆盖新结果 | 乱序提交测试；历史行数与天数一致 |
| 5 Agent 更新 | 输入变化（新视频、主题变化）或模型版本变化时到期；未变化按长间隔；沿用 M2 输入快照与 `INPUT_MISMATCH` 重算 | 模型版本变更后在约定天数内全部重算；输入未变时不重复推理 |
| 6 控制台 | 纳管频道列表（到期时间、上次成功、失败原因）；暂停/恢复纳管；"立即更新"某个领域；更新计划与首次采集计划区分显示 | 浏览器验收；只读账号看不到写操作 |
| 7 验收 | 一组真实频道连续多日自动更新，含中断恢复、重复提交、乱序提交、预算耗尽 | 见下文"验收" |

## 更新间隔：沿用旧系统算法（2026-10-08 改定）

先上线的 v1 固定分档已撤下。旧系统 `services/feature-engine` 的时钟算法（策略 `v16-rule-7`）运行稳定，按原逻辑用 TypeScript 重写为 `packages/feature-clock`，不接旧服务、不改算法：

- **来源**：crawlSystem `e92d9227`，`policy.py`、`state.py`、`shared_features.py` 与 `applier.py` 中的时钟编排；策略参数文件原样复制（`clock_policy_v16_rule_7.json`）。只搬了该策略实际启用的分支（节奏基线、动态基线），关掉这些开关的旧分支没有搬，加载这类策略会直接报错。
- **一致性**：用旧代码生成对照数据后逐条比对。300 个模拟频道、2300 多次采集，每一步的到期日、天数、原因代码、频道特征全部一致（`test/parity.test.ts`）；另有 1 万个卡在各阈值附近的边界样本（`test/probes.test.ts`），以及按旧单元测试改写的规则测试（`test/legacy-rules.test.ts`）。唯一允许的差别是"发布规律度"的最后一位小数：它用到指数函数，Node 与 C 库的结果可能差 1 个最小单位，不会改变任何天数。生成脚本在 `parity/`。
- **Python 细节照搬**：`round` 四舍六入五成双、`sum` 补偿求和、`pstdev` 精确方差后正确舍入、`timedelta` 微秒舍入、时间精确到微秒、到期日按 UTC 自然日。

算法要点（旧系统原样）：

| 时钟 | 怎么定间隔 |
| --- | --- |
| 频道资料 | 首次：按发布节奏 1/2/3/5 天，看不出节奏按 7 天。之后：订阅增长 40% + 播放增长 35% + 视频数变化 20% + 采集优先级 5% 综合分档（1～180 天）；增长排名前 10% 每天；有发布节奏时不超过节奏档；视频数增加且 30 天内发过视频时 3 天内再看；长间隔需要先稳定（21 天且 3 次→14 天档，60/6→30，120/9→60，180/12→90，365/15→180）；每次最多放慢一档，加快不受限；部分成功 3 天内补 |
| 视频 | 取"发现新视频"和"复查近期视频"两者中更短的，最短 3 天。发现：发布规律（规律度 ≥ 0.65）时赶在预计下一条之前查；不规律时按发布概率并随沉默变慢，连续查空再放慢（最多 3 倍）；最长 90 天 |
| Agent | 首次 180 天；之后按画像变化幅度连续取值，变化越小越久（60～365 天）；Agent 版本变化后重新起算；按频道固定错峰顺延几天 |
| 失败 | 时钟完全不动，保持到期，下一轮调度再做（旧系统做法；`retry_at` 不再使用） |

每天（UTC）由调度程序把所有频道的订阅数、订阅增长、播放增长做一次排名分布（增长按订阅规模分组，组内不足 20 个频道时用全体），并据此刷新每个频道的排名特征；时钟只在下一次采集后按新排名重算。

新系统与旧系统的差别（如实记录）：

- **近期视频复查要到第 3 步才有**。此前每次视频更新按旧系统"复查跳过"处理，视频时钟因此最长 7 天；"近 30 天视频数"也要等复查才有，相关加分暂时为 0。
- **没有"用户查询热度""人工优先级"两个信号**，按 0 计（旧系统多数频道也是 0）。
- **旧系统由爬虫判定的"休眠频道"**（长期不更新改为低频复查）没有搬，留到有长期数据后再看。
- **Agent 输入的映射**：旧系统的主题词与证据指纹由爬虫生成；新系统用画像里的一级/二级分类和 10 个标签作主题词，用各项事实引用的证据和来源链接做指纹，模型版本 + 分类体系版本作 Agent 版本。

允许的天数集合与人工指定间隔不变：1/2/3/5/7/14/30/60/90/180/365 天。

## 第 2 步：调度约束

- **同一频道一个活动计划。** 计划执行期间另一个领域到期：不修改已冻结的 `required_domains`，记录到期事实，本计划结束后再安排（方案第 7 章）。
- **预算分开设。** 每日 Data API 配额、代理并发、Agent 推理并发、计划并发分别设上限；扩 Worker 不自动放大这些额度。M2 实测每个频道约 3 个 Data API 配额单位，默认单项目每日 10,000 单位，约可支撑每天 3,000 次频道更新（待真实统计校正）。
- **公平。** 到期越久越优先；人工"立即更新"插队但计入预算。

## 验收

1. 时间压缩测试：注入时钟，一个频道走完首次采集 → About/VIDEO/Agent 各自到期 → 七种组合计划全部出现过 → 失败只按重试间隔补做。
2. 重复与乱序：同一批次重复提交不重复生效；旧计划的迟到结果不覆盖新计划结果；视频、评论、画像实体数不随更新次数增长。
3. 真实小样本：约 20 个真实频道连续自动更新至少 3 天；新发布视频被发现；Worker 中途替换、Profile Agent 下线后恢复。
4. 预算：人为把配额或代理并发调低，计划进入等待并在额度恢复后继续，不丢、不重复。

## 决定（2026-10-08 确认）

| 编号 | 问题 | 决定 |
| --- | --- | --- |
| M3-D1 | v1 用固定分档还是直接上动态规则 | 先定为固定分档；同日改定：直接沿用旧系统算法（v16-rule-7），重写为新代码，逻辑不变 |
| M3-D2 | "近期视频刷新"的范围 | 与首次采集一致：最近 30 个、90 天内 |
| M3-D3 | 评论是否随更新刷新 | 只对新发现的视频采首屏评论；旧视频不重采 |
| M3-D4 | 验收用的频道数量和来源 | 约 20 个，覆盖高频、低频、长期不更新三类 |
| M3-D5 | 调度器上线后自动更新哪些内容 | 先只自动更新频道资料（成本低，用来在真实环境验证调度）；视频等第 3 步增量采集、Agent 等第 5 步再开。其余到期内容可在"更新采集"页手动"立即更新"（2026-10-08 确认方案 B） |

代理前提已满足：节点代理改为内容探测、先试用后使用、反复失败自动淘汰（`7e59334`），订阅支持 Clash（`dd55bbd`、`ffb1c11`）；s2 接入两个公共订阅后，真实频道端到端验收通过，见 [reports/real-channel-20261008-proxy-lifecycle.json](reports/real-channel-20261008-proxy-lifecycle.json)。

## 进度

| 步骤 | 状态 | 提交 |
| --- | --- | --- |
| 1 纳管与 Clock | 完成：真实频道首个计划完成即纳管，三个 Clock（频道资料、视频、Agent，同 24.8 §7）；操作员可纳管、暂停、恢复、移出（版本校验），可按类型人工指定间隔；时钟由旧系统算法计算（见上） | 见下 |
| 2 调度器 | 完成：调度程序每 30 秒扫描到期时钟，每个频道生成一个冻结的更新计划；按 M3-D5 先只自动更新频道资料；"更新采集"页接入真实数据并可手动"立即更新" | 见下 |

第 1 步的实现说明：

- **数据**：`m1.channels` 增加纳管状态与版本；`m1.channel_clocks` 每个纳管频道三行，是对外的生效时钟（人工间隔已叠加），`reasons` 记录原因代码（迁移 009、010、011、012）。`m1.channel_feature_state` 存每个频道的算法状态：频道特征、算法自己的三个时钟、各类型已处理次数、各类型最近一次的原因；`m1.feature_reference_distributions` 存每日排名分布（迁移 012）。
- **计划结束时**（完成、失败、超时、取消，同一事务内）：本计划要求的每个类型按旧系统的"一次采集结果"喂给算法——资料用三项计数（全部拿到算完整，否则算部分）；视频只算本计划首次采到的视频（之前的计划没采过）；Agent 用画像。没完成的类型记一次失败，时钟不动。代码在 `packages/store/src/feature-clocks.ts`。
- **纳管**：首个计划完成即纳管，算法从这个计划起算。手动纳管或重新纳管时，算法用库里已有的资料、视频、画像从头起算（移出期间采到的也算上）。已移出的频道不再被后续计划改动，也不会自动重新纳管。
- **人工指定间隔**（2026-10-08 确认方案 B）：按频道、按类型固定间隔，覆盖算法结果；下次 = 上次成功那天（没有则今天）+ 指定天数。算法照常在后台跟进，恢复"自动"即回到算法当前的结果。

第 2 步的实现说明：

- **自动调度**（`Store.scheduleUpdates`，调度程序每 30 秒一次）：只看 `auto_domains` 里的时钟（默认只有频道资料，环境变量 `UPDATE_AUTO_DOMAINS` 可改，如 `ABOUT,VIDEO`；`UPDATE_SCHEDULER_ENABLED=false` 全部暂停）。到期且今天（UTC）还没安排、也没尝试过的时钟才会安排，按旧系统做法每个时钟每天最多一次；失败后时钟保持到期，第二天再试。同一频道同时只有一个活动计划（数据库唯一索引兜底），多个调度程序同时扫描也只建一个。计划类型 `UPDATE`，冻结本次要更新的内容；只更新 Agent 时冻结已有视频作为输入。
- **预算**：活动计划上限（默认 2）、Agent 计划上限（1）、每日更新计划上限（100）、Data API 每日配额（10,000 单位，按太平洋时间午夜重置）。建计划时按最坏情况预留配额，计划结束释放未用部分；Worker 每次真实调用 Data API 前先领一张许可，额度用完就停下，计划失败、时钟保持到期。迁移 013。
- **手动更新**（`POST /v1/channels/:id/update`，操作员）：不受自动范围限制，默认更新所有到期内容，也可指定；同样受预算约束，重复点击按同一请求编号只建一个计划。
- **控制台"更新采集"页**：到期、排队、执行中、逾期、近 24 小时完成/失败、预算用量、每个频道的等待原因（含"暂未开启自动更新，可手动更新"）；更新策略面板注明哪些内容自动更新。
- **控制台**：频道管理侧栏"更新策略"与频道详情共用同一组件，显示三个 Clock 的间隔、下次时间、状态与上次成功，鼠标悬停"每 N 天"显示原因（旧系统原因代码的中文说明，全部原因都有说明，测试覆盖）；操作员可调整间隔和纳管状态；列表"下次更新"显示最早一天及当天要更新的内容。
